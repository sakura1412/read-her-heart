# 05 Solution Analysis — 方案分析

## 目标

依次回答七层决策的第 3、4 层：**用户提出的方案是不是正确方案？有没有更便宜的替代方案？**

本文件有两种用法，按需求 ID 独立选择：普通模式用于评价和比较候选方案；已由用户明确绑定强制执行且仍在适用范围内的需求，按下方“强制执行用法”生成方案，不把方案阶段跳过，也不重新评价需求是否值得做。模式继承与变更见 [强制执行模式](mandatory-execution.md#作用范围与继承)。

## 强制执行用法

强制执行时不要求问题、价值或证据门槛成立。将用户已确定的目标发展为可写入 PRD 的方案，至少定义：目标角色与触发条件、主流程与状态、业务规则、范围与非目标、异常与兜底、数据与权限、依赖与约束、验收方向。

- 已确认内容直接写入方案。
- 为保证方案连贯而补充的内容标记为“假设”。
- 缺少产品决策的信息标记为“待确认”。
- 架构、接口、容量、性能、成本或工期等研发判断标记为“待技术确认”，不得替研发决定。
- 安全、权限、隐私或合规未知项标记责任方和关闭节点；不得以“必须做”为由默认放宽约束。
- 主方案存在明显违法、有害、越权或不可接受安全风险时，改为满足同一目标的合规替代方案；无法安全实现时明确阻断项。

仅当用户已要求或授权查询/总结相关公开信息、且外部事实有助于定义可执行方案时，按[外部扫描规则](external-scan.md)核查可用替代产品或约束；不得借此恢复“是否值得做”的评估门槛。

产出“强制执行方案摘要”后进入 [09 验收标准](09-acceptance-criteria.md)，再由 10 生成 PRD；不输出做/不做、投入优先级或证据充分性结论。

## 普通模式分析步骤

1. 将用户方案还原为“通过什么机制解决哪一个根因”，检查它是否适配真实任务；已有系统改造检查与已核实现状的关系，0→1 新建检查拟建系统边界与现有业务/替代路径，不虚构既有产品能力。
2. 明确方案的用户流程、覆盖范围、边界、异常、权限、采用成本和可能副作用。
3. 只保留适用的替代项进行比较：不改、配置现有能力、修复缺陷、优化流程、培训/引导、人工运营、复用相邻能力、缩小范围、购买第三方服务、新建功能。
4. 对每个候选比较：根因命中度、预期价值、用户负担、可行性、风险、可逆性、长期维护和证据强度。
5. 技术名词、页面或 AI 能力默认是候选方案；不得因“最佳实践”“竞品已有”或“领导指定”跳过替代比较。

当竞品能力或采购替代项可能改变候选方案，且用户已要求或授权查询/总结公开信息时，按[外部扫描规则](external-scan.md)做快速竞品对比与采购/自建比较，并把有来源的发现并入下表；没有扫描时不把“采购”默认为可用或不可用。

## 退出条件

- 选出一个有证据支持的推荐候选，说明对其他适用方案的取舍，再进入 06；有合理备选时一并记录，不因缺少备选阻断唯一可行候选。
- 用户原方案不成立但问题和价值成立时，记录原方案被否决的理由，继续第四层比较替代方案，不把后续层标为“不适用”。选出替代候选后继续判断该候选的可行性、证据和风险；不要求原方案重新通过。
- 替代方案成本未知或不更便宜，不等于没有适用方案；如实记录成本未知项和适用性。
- 只有候选但关键机制待证时进入 07 验证；比较适用替代项后仍无合理候选时，才因“无方案”进入不投入或重新定义问题。
