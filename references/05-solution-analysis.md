# 05 Solution Analysis — 方案分析

## 目标

依次回答七层决策的第 3、4 层：**用户提出的方案是不是正确方案？有没有更便宜的替代方案？**

本文件有两种用法：普通模式用于评价和比较候选方案；当前用户明确启用强制执行模式时，按下方“强制执行用法”生成方案，不把方案阶段跳过，也不重新评价需求是否值得做。

## 强制执行用法

强制执行时不要求问题、价值或证据门槛成立。将用户已确定的目标发展为可写入 PRD 的方案，至少定义：目标角色与触发条件、主流程与状态、业务规则、范围与非目标、异常与兜底、数据与权限、依赖与约束、验收方向。

- 已确认内容直接写入方案。
- 为保证方案连贯而补充的内容标记为“假设”。
- 缺少产品决策的信息标记为“待确认”。
- 架构、接口、容量、性能、成本或工期等研发判断标记为“待技术确认”，不得替研发决定。
- 安全、权限、隐私或合规未知项标记责任方和关闭节点；不得以“必须做”为由默认放宽约束。
- 主方案存在明显违法、有害、越权或不可接受安全风险时，改为满足同一目标的合规替代方案；无法安全实现时明确阻断项。

产出“强制执行方案摘要”后直接进入 09，不输出做/不做、投入优先级或证据充分性结论。

## 普通模式分析步骤

1. 将用户方案还原为“通过什么机制解决哪一个根因”，检查它是否适配真实任务和现有系统。
2. 明确方案的用户流程、覆盖范围、边界、异常、权限、采用成本和可能副作用。
3. 只保留适用的替代项进行比较：不改、配置现有能力、修复缺陷、优化流程、培训/引导、人工运营、复用相邻能力、缩小范围、购买第三方服务、新建功能。
4. 对每个候选比较：根因命中度、预期价值、用户负担、可行性、风险、可逆性、长期维护和证据强度。
5. 技术名词、页面或 AI 能力默认是候选方案；不得因“最佳实践”“竞品已有”或“领导指定”跳过替代比较。

## 退出条件

- 选出一个有证据支持的推荐候选及备选，并说明为什么不选其他方案，再进入 06。
- 用户方案不成立但问题和价值成立时，不否定问题；回到替代方案。
- 只有候选但关键机制待证时进入 07 验证；没有合理方案时进入不投入或重新定义问题。
