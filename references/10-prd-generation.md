# 10 PRD Generation — PRD 生成

进入本阶段前读取 [09 验收标准](09-acceptance-criteria.md)，复用已生成的需求/功能编号、验收条目及待确认项；PRD 不另起一套相互矛盾的验收标准。方案或范围变化影响验收时，先更新 09 中受影响的条目，再同步 PRD。

## 两种 PRD 入口

### 普通模式：PRD 准入门槛

正式 PRD 只在以下条件同时满足时生成：

1. 需求已拆分、分类，目标用户与场景明确。
2. 问题和价值至少成立，核心证据达到实施决策所需强度。
3. 推荐方案及更便宜替代方案已经比较，范围和非目标明确。
4. 产品、交互、技术、数据、运营和合规可行性已确认或有明确责任人及关闭条件。
5. 不存在不可接受风险；验收对象/方向、停止和回退条件可定义。
6. 08 的投入程度为“实施投入”。
7. 09 已逐功能点形成 QA 可据以编写测试用例的验收标准；使本期关键条目无法判定的未知项已关闭。

未达到门槛时，不用完整 PRD 掩盖未知项。输出“PRD 阻塞清单”，指明缺失阶段、待验证假设、责任方和回到哪一阶段。验证投入默认输出实验/验证 Brief，不输出正式 PRD。

### 强制执行模式：方案后生成

需求已由用户明确绑定强制执行且仍在适用范围内时，读取 [强制执行模式](mandatory-execution.md)、[05 方案分析](05-solution-analysis.md) 和 [09 验收标准](09-acceptance-criteria.md)。仅对该范围跳过问题、价值、证据与优先级门槛，但必须先生成方案摘要和验收条目，再据此生成对应复杂度的正式 PRD。不得输出 PRD 阻塞清单代替 PRD；未知信息写入“假设与待确认项”，不自行编造。

混合请求按需求 ID 分别检查入口。已满足普通门槛的需求与完成方案的强制需求可按用户要求合入同份 PRD，但必须逐项标明模式和决策来源；尚未通过普通门槛的需求另列评估/验证事项，不写入正式交付范围，也不标为“由强制指令跳过”。修订已有 PRD 时同样检查新增范围，不能因文档原为强制模式就自动纳入。若未决事项是已纳入范围的必要依赖，显式标记该依赖及其对交付的影响，不暗示已经批准。

## 按复杂度选择 PRD 详略

复用 01 的[五维复杂度判断](complexity-assessment.md)，在达到本节适用的 PRD 入口后确定文档层级。复杂度决定写法与篇幅，不改变普通模式的准入条件，也不改变强制模式的方案步骤。用户明确要求更详细的文档时可以展开；写作中发现影响范围或风险变化时更新复杂度并调整层级。

| 复杂度 | PRD 写法 | 必要内容 |
| --- | --- | --- |
| 简单，五维均有依据为低 | **简版**：用少量段落或项目直观写清，省略不适用的章节和重复的分析过程 | 文档身份与范围；谁在什么场景下需要什么、系统如何响应；适用的关键规则；复用 09 中对应功能编号的可测试验收标准。只有涉及权限、数据、异常或待确认项时才补充相关约束 |
| 中等复杂，或复杂度待确认且临时按中等档分析 | **标准版**：保留简版主线，按实际影响补充流程、状态、角色、数据权限、异常、依赖与验收；可合并章节，不要求下方 12 项全部成章 | 清楚表达跨步骤/角色的行为及边界，记录会影响交付的风险和待确认项 |
| 复杂/战略，或已知高影响而暂按复杂档处理 | **完整版**：使用下方现有 12 项结构，根据实际范围展开证据、流程、数据权限、风险、发布与追溯 | 多角色、多系统、敏感数据、不可逆操作或级联影响必须有相应规则、异常、控制和验收 |

三种写法都属于正式 PRD。简版可以缩短背景和章节，但不得把逐功能点的 AC 合并成一句泛化验收；完整版也不为凑章节重复内容。混合需求可逐项按复杂度写，不用一个高复杂度事项迫使其他独立事项都采用完整版；共享依赖和风险在相关位置说明。强制执行的简单需求同样可用简版，但必须保留模式、已确定目标、适用方案、假设与待确认项，以及安全、权限、隐私和合规约束。复杂度不明时先使用已确定的临时分析档位，不把未知默认为简单。

达到 PRD 入口后，默认按层级选用[简版](../templates/prd-simple.md)、[标准版](../templates/prd-standard.md)或[完整版](../templates/prd-full.md) Markdown 模板作为源稿骨架。模板不是准入证明；只保留实际适用的章节，替换全部占位内容，不让空表或示例语句进入正式 PRD。普通模式仍先通过本文件的准入门槛；强制模式仍先完成方案和 09 验收，不因模板存在而扩展强制范围。

### 复杂/战略需求的完整结构

1. **文档信息**：标题、状态、负责人、相关方、版本、日期、决策记录链接或来源；强制执行时注明模式和被跳过的评估门槛。
2. **背景与问题**：目标用户、场景、当前行为、问题证据、根因及不解决后果；强制执行时只写已知背景，未评估的内容明确写“由强制指令跳过”，不得补造问题或价值依据。
3. **目标与非目标**：用户/业务目标、影响指标、基线、预期变化和明确不做事项。
4. **范围**：本期范围、后续范围、角色与权限、平台/地区/客户边界。
5. **用户流程与故事**：主路径、异常路径、状态变化，以及“作为…我希望…从而…”。
6. **功能需求**：使用稳定编号（FR-001…），写触发、前置条件、规则、结果和异常。
7. **数据与权限**：字段、来源、口径、访问控制、保留、审计、迁移和埋点。
8. **非功能需求**：性能、可靠性、安全、隐私、可访问性、兼容和可观测性；没有依据的目标标为待确认。
9. **验收标准**：写入 09 已形成的可测试条目，保留稳定 AC 编号与对应功能编号；必要时更新受影响的 09 记录，不在 PRD 内另造冲突规则。
10. **发布与运营**：灰度/迁移、培训、客服、监控、告警、回退和长期维护。
11. **依赖、风险与开放问题**：责任人、关闭条件和截止点；不隐藏待定项。
12. **决策追溯**：普通模式使用“需求 ID → 问题/价值证据 → 方案 → 功能需求 → 验收标准 → 指标”；强制执行模式使用“用户强制执行指令 → 方案条目 → 需求 ID → 功能需求 → 验收标准”。

## 写作规则

- 标明项目形态。0→1 新建的“当前”描述业务做法或替代路径，不写不存在的目标系统现状；已有系统改造区分已实查事实、文档/用户描述与未知项。新建并对接旧系统时分开写新建范围与旧系统依赖。
- 描述产品行为和验收结果，不替研发虚构架构、接口、工期或实现细节。
- 区分已确认要求、假设、待技术确认和未来项；不要把开放问题写成确定事实。
- 将 09 的验收条目按本期功能点写入 PRD，保留 `需求 ID → FR → AC` 映射与场景、前置、触发、预期结果；不要只列 AC 标题或笼统地写“测试通过”。强制执行中条件或阈值未知时，显著列出受阻的 FR/AC、责任方与关闭点，沿用“QA 编写受阻／验收判定待定”状态，不伪称该项已经可测。已有标准不在聊天和文档其他章节重复铺陈。
- 普通模式下，每个功能需求必须能追溯到已成立的问题或价值目标；强制执行模式要求追溯到用户指令、方案条目和需求 ID，不补造问题或价值证据。
- 保持范围可交付。普通模式的实施投入不等于一次性交付全部设想，优先写经 08 确认的受控或分阶段范围；强制需求以用户指令绑定的范围为准，不要求补做 08，也不扩展到未纳入的需求。
- 按对应层级覆盖适用内容，不为凑齐结构重复叙述。业务规则和功能行为只完整定义一次；流程、权限和验收处引用需求编号，补充各自独有的信息。简版不强制背景、指标、用户故事、运营等独立章节；实际受影响的规则、异常、权限、数据和验收仍须写清。
- 假设、风险和开放问题集中管理，相关条目处保留简短标记或编号引用，避免在背景、方案、风险和总结中复制整段说明。验收标准仍须可测试、可追溯，不能只写“同上”。
- 聊天默认只交付简短状态、文件链接和需用户决策的事项；完整分析与 PRD 留在源稿/PDF，用户要求时再展开。

## 内容确认（导出前一次）

PRD 完成后一次性确认：所有层级均需目标和范围一致、逐功能点的 FR/AC 映射无遗漏、已确定条目足以让 QA 写出可判通过/失败的用例；不能判定的条目显式标记并有关闭点。涉及异常、权限、数据、指标、风险或待确认项时检查相应内容。完整版再确认多角色主/异常流程、跨系统依赖、指标可观测、发布与回退、风险责任人和追溯关系。已在写作中确认的内容不为导出 PDF 再跑一遍评估。普通模式的重大缺口应回到对应阶段；强制执行模式不回退评估流程，将缺口保留为显式待确认项。

## PDF 文件交付（两种模式通用）

默认交付对应层级正式 PRD 的可下载 PDF，同时保留同版本可编辑源稿（如 Markdown）。简版、标准版和完整版都适用同一文件交付规则。除非用户明确指定其他格式，不能只在聊天中输出正文或要求用户自行复制、打印为 PDF。PDF 是交付格式，不改变普通模式的准入门槛或强制模式的方案步骤；仅完成分析、验证计划或阻塞清单时，不为导出 PDF 擅自生成 PRD。

1. **确定内容**：将已完成的 PRD 保存为源稿，记录本次应交付的功能需求与验收编号集合（如 FR-001、AC-001），并在源稿所有正文、验收、风险与附录之后保留一个当前文档/版本的结束标记，例如 `PRD-END:customer-import:v1.0`。标记随正文一次导出，不放在页眉、页脚或目录，也不在导出后独立补入 PDF；修订时同步版本和编号集合。强制执行时将方案摘要、执行模式、跳过的评估项、假设与待确认项一并收入 PDF，保持需求编号和验收标准一致。保留原有草案/待确认状态，导出不代表批准上线。
2. **快速导出**：复用现有本地工具和中文字体，一次生成 PDF；若本地 HTML→PDF 工具可用，可将同版 Markdown 渲染成 HTML，套入仓库随附的 [A4 中文打印模板](../templates/prd-a4.html) 后导出；该 HTML 文件本身不是 PDF。无此工具时沿用其他可用本地方式，不为普通导出安装额外渲染器、切换多个引擎或反复美化。可参考环境中的 PDF 技能获取工具用法，但本项目采用用户明确要求的快速交付策略，不因通用技能的默认流程恢复逐页截图检查。将表格正常排版；流程图工具不可用时使用保留节点与分支含义的文字流程，不把源码当图，也不为装饰性图形阻塞导出。
3. **排版**：默认 A4、可嵌入中文字体、可搜索正文，包含标题、版本、日期、状态和页码。A4 模板提供中文字体栈、打印边距、页码和跨页样式；具体字体嵌入与页码效果仍取决于导出器，不支持 CSS 页码时用本地导出器的页脚设置补足。复用自动换行和跨页表头设置；宽表拆分或横向排版。目录按需要添加，不为短文档生成额外封面、目录或多轮排版。
4. **最小检查**：一次解析 PDF 并提取全篇文本，在同一次结果上确认：文件存在且非空、至少一页、正文文本非空、当前版本的结束标记出现在正文末尾、源稿记录的应交付功能需求与验收编号均无缺失。允许规范化换行和空白，编号按完整编号匹配，不能用旧版本标记或从导出结果反推预期编号。发现缺失即不通过，不能仅因首页非空判成功。此检查用于发现尾部截断和编号遗漏，不代表逐字完整性或全量视觉检查；默认不逐页转图、不全文逐项比对、不重复审查产品内容。
5. **交付**：在用户指定目录或当前任务的可写输出目录保存，例如 `output/pdf/<需求名>-PRD-v1.0.pdf`，并保留同版本源稿。避免覆盖用户已有版本。最终回复给出简短摘要、实际 PDF 附件或宿主支持的可点击文件链接；本地文件链接使用真实绝对路径，不编造下载地址。可另附源稿链接供修改。
6. **异常处理**：只有导出报错、空白正文、结束标记或需求编号缺失、中文字体/溢出警告、复杂宽表或自定义布局存在明确风险，或用户要求精细检查时，才检查受影响的内容或页面。提取失败或标记/编号不匹配时，定位排版、截断或文本提取问题，不删除预期项、伪补标记或改成“仅首页有字即通过”；必要时只渲染相关页。修复并重新导出后做一次最小检查，不自动扩大为全篇逐页审查。导出失败时尝试一个可用的本地替代方式，仍失败则保留源稿并说明具体缺口。不得把 Markdown 改名为 PDF，也不得声称文件已交付；不得为取得下载链接擅自上传业务文档到公开 GitHub 或外部转换服务。

PDF 通过最小检查且没有已发现的未解决异常、提供实际可访问文件后，即完成默认交付。后续修改时同步源稿和 PDF，重做一次最小检查；仅对变动引发的明确异常追加局部检查。
