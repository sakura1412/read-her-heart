# 10 PRD Generation — PRD 生成

进入本阶段前读取 [09 验收标准](09-acceptance-criteria.md)，复用已生成的需求/功能编号、验收条目及待确认项；PRD 不另起一套相互矛盾的验收标准。方案或范围变化时，先按[需求变更分析](requirement-change.md#范围变更的联动更新)核对原版本、待决变更和关联影响，联动 FR、AC、指标及验收覆盖，仅更新受影响内容并写入正文变更记录。仅被要求分析变更时不改写已批准 PRD；确认采纳并获准修订后，保留旧版本，给新源稿/PDF 标明版本、变更 ID 与生效范围。受未决冲突影响的交付范围不得被写成已确认规则，未受影响部分可继续。

## 两种 PRD 入口

### 普通模式：PRD 准入门槛

正式 PRD 只在以下条件同时满足时生成：

1. 需求已拆分、分类，目标用户与场景明确。
2. 问题和价值至少成立；07 已按具体假设与判据引用证据台账，说明核心证据为何足以支持该实施范围，不能仅以证据条数或“强”标签代替判断。
3. 推荐方案及更便宜替代方案已经比较，范围和非目标明确。
4. 产品、交互、技术、数据、运营和合规可行性已确认或有明确责任人及关闭条件。
5. 不存在不可接受风险；验收对象/方向、停止和回退条件可定义。
6. 08 的投入程度为“实施投入”；复杂/不可逆范围已完成适用的[事前验尸与反方评审](premortem-review.md)或复用仍有效的实施评审，关键实施缺口已关闭，不用早期验证评审替代。
7. 09 已逐功能点形成 QA 可据以编写测试用例的验收标准；使本期关键条目无法判定的未知项已关闭。

未达到门槛时，不用完整 PRD 掩盖未知项。输出“PRD 阻塞清单”，指明缺失阶段、待验证假设、责任方和回到哪一阶段。验证投入默认输出实验/验证 Brief，不输出正式 PRD。

### 强制执行模式：方案与风险记录后生成

需求已由用户明确绑定强制执行且仍在适用范围内时，读取 [强制执行模式](mandatory-execution.md)、[05 方案分析](05-solution-analysis.md)、[06 轻量风险知情单](06-feasibility.md#强制执行轻量风险知情单)和 [09 验收标准](09-acceptance-criteria.md)。仅对该范围跳过问题、价值、证据与优先级门槛，先生成方案摘要、风险知情单和验收条目，再按用户选择的类型生成正式 PRD；类型未选时按下文询问。普通未知、决策人或风险接受记录缺失时不以阻塞清单代替 PRD，但必须如实保留待确认，不推定风险已获接受；不可接受的安全、权限、隐私或合规冲突按 06 调整或阻断受影响范围。

风险知情单用[专用模板](../templates/risk-acknowledgement.md)，默认同目录独立交付 Markdown，并把同版同内容完整复用为 PRD 的专门风险章节；不能只在 PDF 中放外链。简版也保留精简风险记录，其他章节只引用风险 ID，避免重复铺陈。默认不额外导出风险单 PDF，不增加独立签字流程。风险单使用关联 PRD 版本（独立 Delta 用自身 dN），保留实际确认来源与待决状态；文档生成不等于上线批准。

混合请求按需求 ID 分别检查入口。已满足普通门槛的需求与完成方案的强制需求可按用户要求合入同份 PRD，但必须逐项标明模式和决策来源；尚未通过普通门槛的需求另列评估/验证事项，不写入正式交付范围，也不标为“由强制指令跳过”。修订已有 PRD 时同样检查新增范围，不能因文档原为强制模式就自动纳入。若未决事项是已纳入范围的必要依赖，显式标记该依赖及其对交付的影响，不暗示已经批准。

### 增量交付（Delta PRD）

用户要求在既有 PRD 上单独交付增量规格时，读取[增量规格](delta-spec.md)，使用 [Delta PRD 模板](../templates/prd-delta.md)。它是交付形态，不是第三种模式：正式增量仍适用上述普通/强制入口，且获批准才更新有效业务基线；仅要求提案时可生成显著标明“提议稿／待决策／不得作为实施依据”的独立 Delta，不把它当作正式实施 PRD，不覆盖原件或占用主 PRD 新版本。普通请求完整正式 PRD 时仍按原门槛，不以草案替代阻塞说明。

Delta 只写本次增/改/废、保留项引用、受影响 FR/AC 和必要影响/冲突，不重复全套 12 项。普通正式增量的关键 AC 仍须明确，强制范围内的普通未知项按原规则保留。所有实际生成的 Delta PRD（包括提议稿）默认交付 PDF+可编辑源稿，用户明确另定格式时遵从；仅只读 Diff 或聊天中的变更分析不触发文件导出。

## 文档版本与本版变更

每份正式 PRD 在开头显示**当前文档版本、日期和状态**。修订版紧接版本信息，显示“相对上一版的变更”，用 1–3 条简短描述概括本版实际纳入的需求、规则或验收变化，并注明上一版版本号；有 `CR` 编号时可附编号追溯。只比较**紧邻的上一份 PRD**，不重复完整历史或把变更分析报告搬进文档。首版标“首版”即可，不虚构上一版或变更摘要。版本和摘要说明文档内容，不表示需求已上线或验收通过。

先读取上版源稿/PDF、版本与已批准的变更记录，再确定本版内容。沿用项目已有版本规则；没有规则时，首版可用 `v1.0`，之后内容修订依次使用下一个未占用的小版本号，不凭主观判断跳大版本。需求卡的 `revision`、`CR` 编号和 PRD 文档版本分别记录，不能互相代替。需求规则、验收或影响理解的文义修订都属于内容变化；若只修正文案而不改变产品规则，摘要如实写“文案修正”，不伪称需求变更。仅重新导出 PDF、调整排版且正文内容未变时，保持同一文档版本和变更摘要，不制造一次“需求变更”；避免覆盖同版旧文件，必要时按导出时间区分文件。上版不可取得或版本链不清时，不猜上一版及差异：先请求可核验来源；必须继续交付时标“版本/相对上版变更待核对”，不声称这是已核对的正式变更摘要。

已批准的变更在新 PRD 中只写**相对上一版已确认纳入的内容变化**；未决或被拒的提议不得列为已完成变更。若多个 `CR` 一起进入本版，按用户可感知的结果合并精简说明，不逐条复制内部论证。源稿、PDF 正文、文件名和 `PRD-END` 结束标记使用同一版本；修订版的 PDF 必须能看到版本及本版变更摘要，不能只在聊天或 Markdown 中显示。

独立 Delta 分开显示业务基线版本、Delta 自身修订（如 `d1`）及拟目标完整 PRD 版本；只生成 Delta 不给完整 PRD 升版。已批准未合并增量及其顺序也是有效基线的一部分。Delta 开头的修订摘要对比上一份 Delta 修订，规则差异对比标明的业务基线；获准整合后，完整 PRD 的本版摘要仍对比紧邻上一份完整 PRD，不能漏掉期间已确认纳入的增量。详见[增量版本与合并](delta-spec.md#4-多次变更版本与合并)。

### 变更影响与记录

PRD 正文保留可追溯的**变更影响与记录**，三种用户选择的类型均适用，简版可压缩为几条或小表，不因此自动升级。首版只写“首版，暂无变更”，不制造空影响表。修订版保留开头 1–3 条摘要，正文在文档信息或决策追溯下集中呈现：

- **变更记录**：CR、时间、提出/决定来源、业务基线与本版版本、变更原因及简述、状态与生效范围。保留历史 CR、版本和真实决定的简短索引；旧分析引用固定版本，不重复全文。未知来源写待确认，不能伪造批准。
- **本次影响**：按[联动规则](requirement-change.md#范围变更的联动更新)列受影响范围及 FR、AC、指标和覆盖/回归；以 `CR / D-ID → 对象 ID 或章节 → 原@版本 → 新规则/处置 → 状态及缺口` 表达。各类核对无影响时合并写依据，资料不足标待核验，不能漏查或强造变化。新规则在所属章节定义，表中只给必要差异和定位，不再复制整段。
- **保留与待决**：明确未变但需回归的条目，以及不变内容的基线引用；受影响的待确认项说明责任方与关闭点。提议/被拒/撤回的 CR 如需提示，单列真实状态，不算本版已生效变化。

指标的旧口径、历史值和实际结果不能被新范围覆盖；新范围基线未知、目标待确认或新旧不可比时在正文可见。验收覆盖只说明哪些场景有 AC、需补或需回归，不意味着测试通过。普通与强制范围沿用原门槛，强制跳过价值评估不要求补造指标，也不免除已有指标、风险和验收的影响核对。

Delta 复用自己的变更记录、差异和 QA 表补充指标/覆盖影响，不另造一份同义表，不重写主 PRD。完整 PRD 修订则保留未变正文及编号，仅应用获准差异，不能把局部更新变成丢弃其余章节。源稿与 PDF 均包含本次必要记录与影响，不能只在聊天或外链提供；内容一致性随原一次检查完成，PDF 仍按原快速导出流程。

## PRD 类型由用户选择

在用户要求生成 PRD、且达到适用的普通/强制入口时，先核对本次交付的类型选择；只做分析、验证或验收标准时不提前询问文档类型。类型控制文档组织与展开程度，不代表需求通过评估、风险已接受或获准上线。

- **已明确选择**简版、标准版或完整版，直接沿用，不重复问。用户明确说“你来选／按你建议”时才允许代选，简短说明所选类型及理由；沉默、界面预选、AI 建议、旧文件名或模板都不算授权。
- **尚未选择**，按[问答式澄清](clarification-dialogue.md)询问一次，说明三种类型的差异并允许自定义。不默认标准版，也不以复杂度自动定档。可问：`这次 PRD 选哪种？简版：需求、关键规则和验收；标准版：加流程、边界与依赖；完整版：展开完整结构与追溯。也可自定义。` 保留两个快捷选项，如“简版”“标准版”，同时明确“完整版”可在“其他”输入；没有结构化 UI 时直接列三类供文字回答，不伪造按钮。
- **未收到选择**，继续不依赖类型的方案、风险和验收整理，但不自行选模板、定稿或导出 PRD。简短说明待答项及续接点，不循环催问。该偏好确认也适用于强制执行，不是恢复问题、价值、证据或优先级评估。

[五维复杂度](complexity-assessment.md)继续决定分析深度与适用规则、风险和验收的必要覆盖，只能用来给出一句可选的类型建议，不能替用户决定。复杂需求选简版仍按简版组织，紧凑补齐必要内容，不自动升级；简单需求选完整版也不编造内容或保留无用空章。复杂度未知不等于默认标准版。

| 用户选择 | PRD 写法 | 必要内容 |
| --- | --- | --- |
| 简版 | 用少量段落或项目直观写清，省略不适用章节和重复分析 | 文档身份与范围；用户场景、功能行为与关键规则；09 的逐功能点可测试验收；适用的权限、数据、异常、依赖、风险、回退与待确认项紧凑写明 |
| 标准版 | 在简版主线上展开必要流程、状态、角色、数据权限、异常、依赖与验收；可合并章节，不要求 12 项全部成章 | 清楚表达跨步骤/角色的行为及边界，记录会影响交付的风险和待确认项 |
| 完整版 | 使用下方 12 项结构，按实际范围展开证据、流程、数据权限、风险、发布与追溯 | 同一规则只完整定义一次，不为凑齐章节重复内容；不适用项省略或简短说明 |

三种写法都属于正式 PRD，均不得把逐功能点 AC 合并成一句泛化验收，也不得因选简版省略实际受影响的安全、权限、隐私、合规、异常或追溯约束。强制模式保留模式、已确定目标、方案和风险知情单，集中记录假设及待确认项；仅压缩表达，不改变事实和风险状态。必要内容较多时说明会略长，不承诺任意页数上限而删掉规则。

在当前工作记录中保留类型与选择来源，无需为此新建文件。同一份 PRD 的修订、继续写作和重导出复用已确认类型；用户明确“沿用上版”也可作为选择，不从文件名猜偏好。范围或风险变化时补必要内容，可建议换型但不擅自更换。新独立需求不继承为永久偏好；批量可由用户统一指定本批类型或按 ID 分别指定，已覆盖项不逐条重问。用户明确要求 **Delta PRD** 已选择增量形态，不再强问三档或扩成完整文档；纯 Diff 不触发类型选择。

首次生成时，确认后选用[简版](../templates/prd-simple.md)、[标准版](../templates/prd-standard.md)或[完整版](../templates/prd-full.md) Markdown 模板作为源稿骨架；自定义按用户确认的组织方式。修订以现有文档为底稿，只补受影响段落和缺失的变更记录，不重新套模板覆盖未变内容。模板不是准入证明；替换全部占位内容，不让空表或示例语句进入正式 PRD。普通模式仍先通过本文件准入门槛；强制模式仍先完成 05 方案、06 风险记录和 09 验收，不因类型选择扩展强制范围。

### 完整版 PRD 的结构

1. **文档信息**：标题、状态、负责人、相关方、版本、日期、决策记录链接或来源；强制执行时注明模式和被跳过的评估门槛。
2. **背景与问题**：目标用户、场景、当前行为、问题证据、根因及不解决后果；强制执行时只写已知背景，未评估的内容明确写“由强制指令跳过”，不得补造问题或价值依据。
3. **目标与非目标**：用户/业务目标、影响指标、基线、预期变化和明确不做事项。
4. **范围**：本期范围、后续范围、角色与权限、平台/地区/客户边界。
5. **用户流程与故事**：主路径、异常路径、状态变化，以及“作为…我希望…从而…”。
6. **功能需求**：使用稳定编号（FR-001…），写触发、前置条件、规则、结果和异常。
7. **数据与权限**：字段、来源、口径、访问控制、保留、审计、迁移和埋点。
8. **非功能需求**：性能、可靠性、安全、隐私、可访问性、兼容和可观测性；没有依据的目标标为待确认。
9. **验收标准**：写入 09 已形成的可测试条目，保留稳定 AC 编号与对应功能编号；必要时更新受影响的 09 记录，不在 PRD 内另造冲突规则。
10. **发布与运营**：灰度/迁移、培训、客服、监控、告警、回退和长期维护。
11. **依赖、风险与开放问题**：责任人、关闭条件和截止点；不隐藏待定项。强制范围复用同版风险知情单，不另写重复登记表。
12. **决策追溯**：在原有需求、方案、指标与验收映射前接入“证据 E → 假设 H → 决策 DEC”，说明证据支持或反驳了什么、形成何种有来源与状态的决定，再关联需求 ID / 指标 → 方案 SOL → 功能 FR → 验收 AC；强制范围沿用指令与强制决定的追溯，不伪造被跳过的评估。

## 证据、假设与决策追溯

生成 PRD 时读取[统一证据台账](evidence-ledger.md)，复用已有 E、H 和决策编号；新决策示例用 `DEC-001`，与 Delta 的差异 `D-01` 区分。证据、假设和决定不是一一对应关系：一个 H 可以同时有支持与反证，一项决定可以引用多个 H；保留真实关联，不为填满链条编造证据、假设、指标或批准。

PRD 引用**台账位置与固定版本、E 编号、H 与 DEC 的记录版本**，并保留足以独立理解的脱敏发现摘要、适用范围、关键反证/局限及决定状态。不能只有无法访问的链接，也不复制整份台账或受限原始材料。简版 PRD 可用一行映射及简短摘要，标准版用必要关联表，完整版写入第 12 项；已有内容用 ID 引用，不重复论证。需要的证据记录尚无独立文件时可在源稿内精简列出，不因记录形式增加新的文件或准入阶段。

适用条件评审时，DEC 引用 `REV@版本`、重要发现与实际处置；PRD 的风险/追溯位置保留必要残余异议及其限制，采纳的方案控制进入对应 FR/AC，不复制全部争论，也不把待决建议写成生效规则。强制范围引用 06 中同版评审与风险记录，不为写 PRD 恢复被跳过的价值门槛；此引用随原内容核对完成，不增加 PDF 检查轮次。

强制执行使用“指令证据 E → 强制决定 DEC → REQ / SOL → FR → AC”，已有方案/风险证据和 H 可按实际关联补充；被跳过的问题、价值或验证假设标“未评估：由强制指令跳过”，不得要求补齐普通价值证据才交付。指令证明用户作了该决定，不证明价值成立、风险已接受或上线获批；风险记录的实际确认状态照常保留。

新证据、反证、来源撤回或适用性变化时，只复核受影响 H、DEC、范围与 FR/AC，不自动撤销整个 PRD。保留旧证据状态和固定版本的历史引用；需修订文档时按实际授权形成新版本，不能让同一 E 编号在旧 PRD 中静默指向不同结论。Delta 仅列受影响的追溯变化，仍有效的基线链通过版本引用保留，未决判断不冒充已采纳决定。

## 写作规则

- 标明项目形态。0→1 新建的“当前”描述业务做法或替代路径，不写不存在的目标系统现状；已有系统改造区分已实查事实、文档/用户描述与未知项。新建并对接旧系统时分开写新建范围与旧系统依赖。
- 描述产品行为和验收结果，不替研发虚构架构、接口、工期或实现细节。
- 区分已确认要求、假设、待技术确认和未来项；不要把开放问题写成确定事实。
- 将 09 的验收条目按本期功能点写入 PRD，保留 `需求 ID → FR → AC` 映射与场景、前置、触发、预期结果；不要只列 AC 标题或笼统地写“测试通过”。强制执行中条件或阈值未知时，显著列出受阻的 FR/AC、责任方与关闭点，沿用“QA 编写受阻／验收判定待定”状态，不伪称该项已经可测。已有标准不在聊天和文档其他章节重复铺陈。
- 普通模式下，每个功能需求必须能通过 REQ / SOL 追溯到已成立的问题或价值目标及相应 E / H / DEC；关系可一对多或多对一，不要求每个 FR 都独占一条证据。强制执行模式追溯到真实指令、强制决定、方案条目和需求 ID，不补造问题或价值证据。
- 保持范围可交付。普通模式的实施投入不等于一次性交付全部设想，优先写经 08 确认的受控或分阶段范围；强制需求以用户指令绑定的范围为准，不要求补做 08，也不扩展到未纳入的需求。
- 按用户选择的类型组织适用内容，不为凑齐结构重复叙述。业务规则和功能行为只完整定义一次；流程、权限和验收处引用需求编号，补充各自独有的信息。简版不强制背景、指标、用户故事、运营等独立章节；实际受影响的规则、异常、权限、数据和验收仍须写清。
- 假设、风险和开放问题集中管理，相关条目处保留简短标记或编号引用，避免在背景、方案、风险和总结中复制整段说明。验收标准仍须可测试、可追溯，不能只写“同上”。
- 聊天默认只交付简短状态、文件链接和需用户决策的事项；完整分析与 PRD 留在源稿/PDF，用户要求时再展开。
- 已生成的 [Mermaid 逻辑图](mermaid-diagrams.md)放入相关方案/流程章节，复用同版源码、图 ID 和 FR/AC 映射，不另起一套逻辑。状态/交互复杂且缺图时按该规则补充；不因采用完整模板就强制两种图，也不把未知分支画成已定规则。Delta 只更新受影响图并标清提议状态。

## 内容确认（导出前一次）

PRD 完成后一次性确认：所有类型均需目标和范围一致、逐功能点的 FR/AC 映射无遗漏、已确定条目足以让 QA 写出可判通过/失败的用例；不能判定的条目显式标记并有关闭点。核对所引用 E / H / DEC 的版本、适用范围与实际状态，关键反证未被省略，不因链条完整就推定批准；这与原内容检查合并，不新增 PDF 检查轮次。涉及异常、权限、数据、指标、风险或待确认项时检查相应内容。强制范围另确认风险单与 PRD 的版本/范围一致、接受来源真实、条件未闭与复盘触发可见；这是同一次内容检查，不增加审批门槛。适用的多角色主/异常流程、跨系统依赖、指标可观测、发布与回退、风险责任人和追溯关系不因选简版免检；完整版按其结构检查，不重复审查相同内容。已在写作中确认的内容不为导出 PDF 再跑一遍评估。普通模式的重大缺口应回到对应阶段；强制执行模式不回退评估流程，将缺口保留为显式待确认项。

修订版在上述同一次内容检查中，按[联动更新](requirement-change.md#范围变更的联动更新)核对 FR/AC、指标口径与覆盖差异、未变内容保留及 CR 的实际状态；必要记录已进入正文。只更新受影响的检查结论，不为记录变更增加整份重新评估或 PDF 检查轮次。

## PDF 文件交付（两种模式通用）

默认交付对应层级正式 PRD 的可下载 PDF，同时保留同版本可编辑源稿（如 Markdown）。简版、标准版和完整版都适用同一文件交付规则。除非用户明确指定其他格式，不能只在聊天中输出正文或要求用户自行复制、打印为 PDF。PDF 是交付格式，不改变普通模式的准入门槛或强制模式的方案步骤；仅完成分析、验证计划或阻塞清单时，不为导出 PDF 擅自生成 PRD。

文件与导出能力以当前宿主实际工具、环境和权限为准，不依赖 Codex 专有工具或预装 PDF 技能。没有文件工具或写权限时，继续完成正文草稿并明确“源稿文件和 PDF 未生成”；能保存源稿但无可用导出器时交付真实源稿并标“PDF 未完成”。这是部分交付，不是默认 PDF 要求已满足；不伪造附件、路径或完成状态。工具与路径适配见[宿主兼容规则](host-compatibility.md)。

Delta PRD 沿用以下流程，但版本取本份 Delta 的修订号，摘要保留其草案/批准状态；结束标记例如 `PRD-END:REQ-001-Delta-CR-003:d1`。应交付编号集合限于本份差异条目与相关 FR/AC，不要求复制整个基线，基线与目标完整 PRD 版本另列。导出不能改变提议或拟作废状态。

1. **确定内容**：将已完成的 PRD 保存为源稿，在开头写当前版本；修订版紧接版本写相对上版的简短变更摘要。记录本次应交付的功能需求与验收编号集合（如 FR-001、AC-001），并在源稿所有正文、验收、风险与附录之后保留一个当前文档/版本的结束标记，例如 `PRD-END:customer-import:v1.0`。标记随正文一次导出，不放在页眉、页脚或目录，也不在导出后独立补入 PDF；修订时同步版本和编号集合。强制执行时将方案摘要、执行模式和同版风险知情单（包括跳过项、未知、实际接受状态和复盘条件）一并收入 PDF；风险章节放在结束标记之前，不另导风险 PDF。保留原有草案/待确认状态，导出不代表批准上线。
2. **快速导出**：复用现有本地工具和中文字体，一次生成 PDF；若本地 HTML→PDF 工具可用，可将同版 Markdown 渲染成 HTML，套入仓库随附的 [A4 中文打印模板](../templates/prd-a4.html) 后导出；该 HTML 文件本身不是 PDF。无此工具时沿用其他可用本地方式，不为普通导出安装额外渲染器、切换多个引擎或反复美化。可参考环境中的 PDF 技能获取工具用法，但本项目采用用户明确要求的快速交付策略，不因通用技能的默认流程恢复逐页截图检查。Mermaid 复用本地渲染器生成同版 SVG/PNG 后嵌入；工具不可用或针对性修复仍失败时，按[逻辑图降级规则](mermaid-diagrams.md#渲染与轻量核对)保留源码，以等价状态转移/交互步骤表承接并说明未渲染，不把源码当图片。用户明确要求图像时须如实标记部分交付。表格正常排版，不为装饰性图形阻塞导出。
3. **排版**：默认 A4、可嵌入中文字体、可搜索正文，包含标题、版本、日期、状态和页码。A4 模板提供中文字体栈、打印边距、页码和跨页样式；具体字体嵌入与页码效果仍取决于导出器，不支持 CSS 页码时用本地导出器的页脚设置补足。复用自动换行和跨页表头设置；宽表拆分或横向排版。目录按需要添加，不为短文档生成额外封面、目录或多轮排版。
4. **最小检查**：一次解析 PDF 并提取全篇文本，在同一次结果上确认：文件存在且非空、至少一页、正文文本非空、开头的当前版本可见，修订版的相对上版变更摘要可见，当前版本的结束标记出现在正文末尾，源稿记录的应交付功能需求与验收编号均无缺失。允许规范化换行和空白，编号按完整编号匹配，不能用旧版本标记或从导出结果反推预期编号。发现缺失即不通过，不能仅因首页非空判成功。此检查用于发现尾部截断和编号遗漏，不代表逐字完整性或全量视觉检查；默认不逐页转图、不全文逐项比对、不重复审查产品内容。
5. **交付**：在用户指定目录或当前任务的可写输出目录保存，例如 `output/pdf/<需求名>-PRD-v1.0.pdf`，并保留同版本源稿。避免覆盖用户已有版本。最终回复给出简短摘要、实际 PDF 附件或宿主支持的可点击文件链接；本地文件链接使用真实绝对路径。宿主不支持本地链接时给出实际路径及打开方式，不编造公网下载地址，也不把未生成的路径当交付。可另附源稿链接供修改。
6. **异常处理**：只有导出报错、空白正文、结束标记或需求编号缺失、中文字体/溢出警告、复杂宽表或自定义布局存在明确风险，或用户要求精细检查时，才检查受影响的内容或页面。提取失败或标记/编号不匹配时，定位排版、截断或文本提取问题，不删除预期项、伪补标记或改成“仅首页有字即通过”；必要时只渲染相关页。修复并重新导出后做一次最小检查，不自动扩大为全篇逐页审查。导出失败时尝试一个可用的本地替代方式，仍失败则保留源稿并说明具体缺口。不得把 Markdown 改名为 PDF，也不得声称文件已交付；不得为取得下载链接擅自上传业务文档到公开 GitHub 或外部转换服务。

PDF 通过最小检查且没有已发现的未解决异常、提供实际可访问文件后，即完成默认交付。后续修改时同步源稿和 PDF，重做一次最小检查；仅对变动引发的明确异常追加局部检查。
