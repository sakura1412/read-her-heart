# 批量需求入池与分批处理

用户要求需求池/分批，或大量候选与信息缺口使一次逐项深入不现实，才用本入口；二三十条尤其适合先轻量整理。少量需求且用户明确要求逐项分析或正式优先级比较时，只做必要的 ID/范围对齐，不把粗筛当成本轮交付。它是 01 前的**条件入口**，不新增第 11 个阶段，也不替代每项需求的十阶段与七层门槛。单项需求不用建立需求池。需要保存独立文件时使用[需求池模板](../templates/requirement-pool.md)；聊天默认只给压缩索引、批次与关键阻塞，不逐项复制七层分析。

## 第一遍：保全、拆分与粗筛

1. 记录本次输入来源、日期、版本与原始序号；复用用户已有 ID，无 ID 才给原子需求分配稳定编号，建立“原始条目 → 原子 ID”映射。一个条目含多个可独立取舍的目标时拆开；疑似同一目标时先关联，核对用户、场景、结果和约束后再归并，保留原文、来源、旧 ID 与归并理由。相同功能名称不必然是同一需求。
2. 按项目或产品线分组，项目形态已知直接复用；未知时对相关组提出一次“已有系统改造还是 0→1 新建”，不向每条重复索要地址或账号。未答复前仍可做 ID、拆分、来源和依赖等分支无关整理，不把现状当成已核实事实。
3. 每项只记粗筛需要的最小信息：规范化问题/目标与候选方案、目标角色/场景、主类型与来源、普通或用户明确绑定的强制模式及范围、已知证据与缺口、五维影响的**初步信号**（未知照写）、真实时效/事故/合规信号及依据、下一动作和负责人。来源标签或截止要求不证明问题与价值；不能用粗筛替代完整五维定级、RICE 或七层判断。
4. 按当前用户的指令逐 ID 识别强制项；列表、会议纪要或他人引述中的“必须做”不自动触发。用户本轮**只要粗筛**时，先记下强制范围与待方案状态，不擅自交付 PRD；用户要求继续交付时，该项进入最小整理 → 05 方案 → 09 验收 → 10 PRD，不被普通价值/证据队列拦住。安全、权限、隐私、合规和真实性仍有效；独立可取舍的新增能力及其他需求走普通模式。

## 依赖图：关系不等于优先级

| 关系 | 记录方式与处理 |
| --- | --- |
| 硬交付前置 | `A → B` 表示 B 的交付确实需要 A 先具备；注明是已核实还是待研发/业务确认。不能凭“看起来相关”设成硬阻断。 |
| 分析/证据前置 | A 的规则、资料或核验结论会改变 B 的判断；优先澄清 A，但不等于必须先开发 A。 |
| 软依赖/复用 | 可以共享能力、设计或数据，原则上可并行；记录联合评估机会，不自动合并需求或收益。 |
| 冲突/互斥与共享资源 | 方案、范围或同一资源窗口可能冲突；标待协调，不臆测团队容量。 |

每条关系记录关联 ID、依据来源、确认状态、阻断的是分析还是交付、确认责任人；只有先后关系才记录方向，互斥与共享资源不强加箭头。检查循环硬依赖：若 A 必须先于 B、B 又必须先于 A，先标“依赖环待拆解/核验”，不得给出伪造的先后顺序。一个底层能力服务多个候选时，记录共享价值与成本，避免在各项中重复计算；底层需求也不因被依赖就自动通过问题、价值或风险门槛。

## 分批：先安排分析，再讨论交付

需求池的“池状态”和最终“决策状态”分开。普通项收录后可为 **待澄清 / 待评估 / 评估中或验证中 / 待 08 决策 / 已决策 / 已归并或撤回**，08 的投入出口另记；强制项独立标为 **待方案 / 方案中 / PRD 已交付（待实施确认）**，关联原始指令与方案、AC、PRD 链接，不写成“已通过 08”或“已经上线”。粗筛不得把“首批分析”写为“立即做”，也不因资料少就判“不做”。

形成分析处理批次时，先识别有真实依据的事故、安全/合规风险与外部截止，及时交给对应负责人核验或处置；这只是时效信号，不是自动实施批准。再优先处理能解锁多个判断的分析前置项、证据较充分且决策窗口近的候选、需要共同澄清的同场景项；信息不足的发澄清或最小验证任务，受**分析/证据前置**阻断的标等待条件。仅有硬交付前置不阻断问题、价值与投入评估，只限制后续交付波次。团队若给了在制品数量或评审容量，按其约束分批；未给时只提出可调整的首批与后续批次，不编造固定 WIP 上限。每批写明为何入批、预期得到什么判断、进入下一批的条件和责任方。

**分析批次 ≠ 交付波次。** 只有普通需求分别完成实施前置判断并由 08 决定实施投入，或强制项完成其方案/验收路径后，才讨论其交付顺序。08 将已确认的硬交付依赖、研发估算与团队容量、真实截止、发布窗口、风险与可回退性叠加到投入决策；价值排序与技术先后可以不同。若工期、容量或依赖尚未确认，只给“若 X 确认，则 Y 可进入下一波”的条件化排期假设及确认人，不填精确日期或承诺版本。用户给出硬截止时如实记录，但可行性仍须责任方确认。明确重排触发条件：依赖改变、验证失败、资源/截止变化、风险升级或需求范围变化。

## 默认交付与更新

- 完整池保留所有输入条目、归并映射、模式及依赖记录；需要文件时用模板，既有池只更新变化的 ID、状态、证据和批次，不重新编号。
- 聊天概览以 `ID/短名、模式或队列、关键风险/截止信号、阻断依赖、池状态、下一动作/责任人、分析批次` 为主；汇总每批数量，只展开首批少量关键项和跨项依赖。用户要求详细池或审计记录时再展示完整表。
- 进入某批后，对该批普通需求分别从 01 继续，按证据推进；不因为它在同一批、同一页面或依赖链上就合并七层结论。08 只比较已达到相应门槛的候选；未准备好的项保留缺口，不为了排队给伪精确分数或实施名次。

需要**跨会话长期维护**时，改用[需求状态持久化](requirement-state.md)：每个原子 ID 存一张结构化卡，Backlog 由卡片生成。需求池模板仍可用于一次性粗筛报告，不作为与 JSON 卡片并行编辑的第二套事实源。将上述“池状态/分析批次”与卡片中的生命周期状态、正式优先级分别记录；归并、拆分和依赖变更保留旧 ID 与决策记录，不直接覆盖原始来源。未提供项目数据目录时，可先完成本轮粗筛，但不能声称已经跨会话保存。

已入池需求发生规则、范围或方案变更时，按[需求变更分析](requirement-change.md)检查依赖图的入边和出边、互斥项及共享资源，并通知受影响需求的负责人复核；不是只改发生变更的那张卡。未决变更在池中保留关联与阻断说明，不能默认为已批准并据此重排交付承诺。
