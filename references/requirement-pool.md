# 批量分诊与需求池

用户要求“批量分诊 / 快速筛一遍 / 需求池 / 分批”，或一次二三十条独立候选使逐项深入不现实，使用本入口。少量需求且明确要求逐项分析或正式比较时，做必要的 ID/范围对齐后继续用户请求，不强行降为粗筛。这是 01 前的**条件入口**，不是第 11 阶段：全量先轻量分诊，只有选中项再进入适用分析；分诊不能代替实施准入判断。

## 第一遍：最小整理、复杂度与去重

1. **保全输入**：记录来源、日期/版本和原始序号，复用已有稳定 ID。一个条目含多个可独立取舍的目标时拆开，建立“原始条目 → 原子 ID”映射。保留原文或可核验的原始材料位置，不只保留改写后的结论。
2. **按项目组确认现状**：已有系统改造 / 0→1 / 混合，已知不重复问，未知只对该组问一次。等待回答仍可整理和作带未知标记的分诊，不推定系统能力，不向二三十条逐一索要地址、账号或完整资料。
3. **每项最小记录**：问题/目标与候选方案分开；角色/场景；主类型与来源标签；普通/强制模式及适用范围；关键事实及来源、一个最影响判断的缺口；五维复杂度；真实风险/时效信号、依赖和下一动作。领导指定、客户强诉求和合同截止是来源或时效信号，不证明价值，也不自动触发强制执行。
4. **五维快速定级**：按[复杂度规则](complexity-assessment.md)，基于现有材料写“业务/系统/用户/数据风险/不可逆性”的低/中/高/未知与关键依据，再给暂定复杂度。未知不当低，已有高影响按复杂处理，其余缺项记待确认、临时中等。这里不为定级先逐条实查，也不为每项展开七层或 5W2H、Whys、KANO、RICE 等框架。复杂度决定后续深度，不能证明价值或直接决定分诊档位。
5. **核实后归并**：目标、角色、场景、范围与约束实质相同才归并至一个主 ID；保留原始 ID/来源 → 主 ID、归并理由和差异。仅疑似重复先关联；相同名称但角色、权限或规则不同不能直接合并。重复反馈不自动算成更多独立用户或独立证据，归并也不算“直接不投入”。不同强制范围不得因归并而互相扩散。

## 第二遍：普通项三档分诊

已有材料用[共享证据台账](evidence-ledger.md)的最小记录/E 引用，来源索引与台账合用，不逐条重复整理同一工单；材料少则保留未知，不为分诊强造完整 H/DEC 或额外取证。台账记录不自动保存业务资料，也不扩大本轮深入名额。

每个归并后的普通主 ID 只给一个档位、一句依据和下一步；可以某档为空。三档是**当前材料与范围下的粗筛建议**，不是 08 投入批准、实施排序或完整七层结论。

| 档位 | 进入依据 | 最小输出与边界 |
| --- | --- | --- |
| **直接不投入** | 有可追溯且适用当前范围的明确停止依据，如已撤回、本期明确非目标、现有能力已核实完全满足同一目标与边界，或问题已被可靠反证且没有相关新证据 | 写“本轮不再深入”的依据/来源、适用范围与重开条件；未做的后续判断合并标未评估。不是永久否决，也不能伪造用户已批准停止。 |
| **需验证** | 问题、用户/场景、范围、当前能力或关键约束存在足以改变判断的缺口 | 写一个关键问题、最小补证方向和责任人（未知则待指定）。只是补证候选，不等于已批准验证投入，不为每项先写完整 Brief。 |
| **值得深入** | 有相关场景证据或合理机会信号，足以继续判断，且当前没有明确停止依据 | 写深入理由、最需要回答的决策问题及依赖。不是价值已成立或批准开发；选中后仍按普通门槛推进。 |

不能因资料少、实现复杂、提出者级别低、用户声音小或依赖待确认就判“直接不投入”；也不能因容易做、老板提出或客户重复提到就判“值得实施”。否定一个危险或无效候选方案不等于否定底层问题：明确拒绝的是哪段方案，保留安全替代路径或问题本身的分诊记录。

**强制项单列，不硬塞三档。** 只有当前用户对具体 ID/范围明确下达强制指令才生效；会议纪要或老板话的引述不是指令。只要求分诊时记录“强制 / 待方案”和下一步，不擅自生成 PRD；用户要求继续交付的范围按最小整理 → 05 方案 → [06 轻量风险知情单](06-feasibility.md#强制执行轻量风险知情单) → 09 验收 → 10 PRD，不恢复普通价值门槛。安全、权限、隐私、合规和真实性仍保留。

## 第三遍：限定首批，不逐条跑到底

- **只要分诊**：交付全量紧凑索引、归并映射、分档数量及建议首批，到此停止；不展开深度评估、实验或 PRD。
- **要求分诊后继续分析**：优先采用用户指定的 ID、数量或范围。未指定数量时，本次默认最多深入 **3 个归并后的独立需求**，明确这是可调整的回复范围，不是团队 WIP 上限或研发容量。符合条件不足 3 项不凑数；没有可直接深入项时给最关键的澄清，不强行展开。
- **选择依据**：结合用户当前决策目标、可核验的窗口期、证据准备度、能解锁多个判断的分析前置及相关价值信号，不按输入顺序、易做程度或来源权威机械选前几。必要时优先澄清“需验证”中的关键前置，只处理其窄问题；形成验证设计后仍须由 08 判断验证成本是否值得。
- **保留其余项**：每项给下一动作/入下一批条件，不能因为不在首批就判价值低，不静默在后续工具调用中把全池分析完。重大事故、安全/合规风险和真实截止须在全池标出并列明需谁处理，不受首批数量限制；实际通知或处置另需授权。

首批普通项承接已整理结果，从最早需要的阶段继续，按复杂度深入、按证据停止；“完整分析”不等于强迫全部十阶段跑完或一律生成 PRD。强制项按其范围单独路由，不能扩散到同批其他项。跨批次复用已有有效结论与验证累计预算/期限/轮次，不能换批清零。

## 依赖与交付：分析先后不等于开发先后

| 关系 | 记录方式与处理 |
| --- | --- |
| 硬交付前置 | `A → B` 表示 B 的交付确实需要 A 先具备；写依据和确认状态。它不自动阻止 B 的问题、价值和投入分析。 |
| 分析/证据前置 | A 的规则、资料或核验结论会改变 B 的判断；可先澄清 A，不等于先开发 A。 |
| 软依赖/复用 | 共享能力、设计或数据，原则上可并行；记录联合评估机会，不自动合并范围或收益。 |
| 冲突/互斥与共享资源 | 标待协调及责任方，不臆测团队容量，也不强加先后方向。 |

记录关联 ID、来源、确认状态、阻断的是分析还是交付、确认责任人。仅确有先后时画箭头；硬依赖成环先标待拆解/核验，不输出虚假的线性顺序。共享价值和成本不重复计算，底层能力不因被依赖就自动获批。

**分诊档位、分析批次、生命周期和正式优先级是四件事。** 粗筛建议不自动把卡片改成“已暂停/验证中/实施中”，不自动填写正式优先级。只有普通范围满足实施前置判断并由 08 决定投入，或强制范围完成其交付路径后，才讨论交付先后；工期、容量、硬依赖未经确认，只给“若 X 确认，则 Y 可进入下一波”的排期假设和确认人，不承诺日期、人日或版本。

## 默认交付与更新

默认聊天只输出一份紧凑表：`ID/目标｜类型与来源/模式｜五维→复杂度｜分诊档位｜关键依据或缺口｜下一步/依赖｜批次`。每个主 ID 一行，另用简短映射保留已归并 ID；所有原始输入都有去向，不能只展示 Top 3 后丢掉其余项。原始数、拆分后原子数、归并后主项数、三档及强制项数量分别说明，避免重复计数。若依据已写表中，结尾只给首批选择与必要的跨项风险，不再复述每项。

需要独立文件时用[需求池模板](../templates/requirement-pool.md)。用户要求跨会话保存且提供/授权项目目录后，按[持久化规则](requirement-state.md)保存 JSON 卡片；可在可选 `analysis` 中记录分诊时间/来源、档位、依据、重开条件、归并关联，并用 `analysis_batch` 记录分析批次。它们是分析记录，不是新的必填 schema 或真实投入决定；`priority` 留待正式实施排序，状态变更需实际依据。长报告用 `links` 引用，不维护并行事实源。没有保存授权或项目目录时不写盘、不声称下次会记得。

既有池只更新变化的 ID、来源、证据和分诊结果，不重新编号或覆盖旧决定。规则、范围或方案变化按[变更分析](requirement-change.md)核对依赖入边/出边、互斥项及共享资源，列出需复核的负责人；通知需另获授权。未决变更不能当作已批准事实重排交付承诺。新证据、范围、风险、依赖或时效改变时重开相关项，不让首轮分诊长期冻结成路线图。
