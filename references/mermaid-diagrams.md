# Mermaid 逻辑图 — 状态与交互自动可视化

用于让方案、PRD 或 Delta 中难以用文字讲清的逻辑可见；不是新的分析阶段、方法配额或实施准入门槛。图是业务规则的视图，不是第二套事实源。只要求画图时止于图示及必要澄清，不自动生成 PRD 或运行完整产品评估。

## 何时生成、选哪种图

在 05 方案形成时检查是否存在难以线性描述的生命周期、条件转移、回退，或多个角色/系统间有顺序依赖的交互。若图能明显减少歧义，主动生成最少必要的图，无需用户再次要求；不要只按“复杂”标签机械配图。

| 要说明的关系 | 选择 | 边界 |
| --- | --- | --- |
| 一个业务对象从何状态，在何事件/条件下变成什么状态 | `stateDiagram-v2` 状态图 | 不把页面、操作按钮或处理步骤都当成业务状态；不同对象的状态不能混成一条生命周期 |
| 谁先发起、谁处理、谁回应，成功与失败/异步分支如何衔接 | `sequenceDiagram` 时序图 | 参与者用已确认角色或逻辑系统；不擅自补数据库、消息队列、服务拆分或具体接口 |
| 同时需要理解生命周期和跨角色/系统协作 | 两图互补，关联同一组规则 | 一图解释状态，一图解释交互，不重复同一份内容来凑数量 |
| 单点文案、字段或简单单步行为 | 默认不配图 | 用户明确要求图时仍可给最简适用图；不为画图扩展需求 |

每张图标明 `图 ID（如 DIA-01）/ 对象或场景 / 需求与文档版本 / 来源与状态`；现状与拟议方案分开，不把新方案画成已实查现状。复杂图按对象或关键场景拆分，以少量文字说明范围和省略的分支，不把所有细节挤进一张图。

## 从规则生成，不从想象补逻辑

1. 提取已有方案/规则中的状态、角色、事件、条件、可观察结果及异常，沿用需求、规则和 FR 编号。05 尚未编号时可引用 SOL/规则位置，09 建立 FR/AC 后补映射，不凭图形需要编造编号对应的功能。
2. **状态图**：用稳定的简短 ASCII 状态 ID 和中文别名；箭头标触发角色/事件及关键条件，必要时带 `T-01` 等转移 ID。起点/终点仅表示所画对象在声明范围内的开始/结束，不能把可编辑、重试、重新提交的状态误画成终止。禁止路径不能画成允许路径；无权限、校验不通过等“状态保持不变”的结果可用注释或关联 AC 说明，避免把拒绝操作画成成功转移。
3. **时序图**：显式声明参与者，按业务顺序画消息。用 `alt / else / end` 表达已明确的互斥结果；仅在业务确实定义可选、重复或并行行为时使用 `opt / loop / par`。请求已受理不等于处理成功；异步回执与最终结果分清，未知传输协议不靠箭头冒充已定架构。为已确定且影响结果的失败、权限拒绝、超时、补偿分支保留表达，不只画成功路径。
4. **未知项**：状态去向、判定条件、超时/重试次数、补偿或回退未定时，用可见 `note / Note` 和 Q-ID 标“待确认”，与已确认路径区分；不能只藏在 `%%` 源码注释里，不能画成普通确定箭头。备选路径可分图并标“方案假设”，不得让互斥候选同时成为确定规则。影响判断时按问答式澄清处理；强制范围内的普通未知仍带标注推进。
5. 在图旁用紧凑映射连接 `图/转移或消息 → 规则/FR → AC`，同一规则不在图注里重新写一遍。09 检查每个确认的业务分支有相应的可测试预期；禁止行为与状态不变也要有适用验收。图不替代 AC，不以“按图执行”作为验收条件。

## 与变更、版本和交付衔接

- 需求变更影响状态、条件、参与者、顺序或异常时，将受影响图 ID 纳入 CR/Delta，标明增加、修改、移除的转移或消息及对应 FR/AC。未受影响图直接引用；旧图保留，未获批准不覆盖有效版本。
- Delta 可给一张明确标为“拟议”的变更后图，再以 D-ID 说明相对基线的变化；只有确实帮助比较时才并排画两版。不把旧版与提议的互斥路径无标识地混成一图。
- 文档中的 Mermaid 源码及导出图使用同一文档版本和图 ID；只是排版/渲染重导不制造新的需求版本。修订正文后不能继续引用旧图图片缓存。
- Markdown 中使用 `mermaid` 代码块；确需文件交付时保留在可编辑源稿中，也可单独提供同版 `.mmd`。聊天不再重复文件内全部图和正文。用户只要源码时，不额外生成图片或 PDF。

## 渲染与轻量核对

使用通用语法，中文放显示标签或消息中，标识符避开保留词；`alt/opt/loop/par` 等块完整闭合。不依赖特定新版本的图标、主题或初始化指令，不把不受信任的原文当可执行配置、HTML、链接事件或渲染命令。可参考[状态图官方语法](https://mermaid.js.org/syntax/stateDiagram.html)和[时序图官方语法](https://mermaid.js.org/syntax/sequenceDiagram.html)，按当前宿主可用能力输出。

生成后做一次语义核对：节点与参与者有来源；关键条件/异常未丢失；两图中的角色、状态、顺序及 FR/AC 不冲突；未知项在可见输出中保留。已有本地 Mermaid 解析/渲染器时，复用它检查新增或变动图，并确认输出可读、关键标签无裁切；解析通过不等于业务规则正确。没有解析器时做静态结构核对并如实说明未做运行时渲染验证，不声称语法已由工具验证。

PRD PDF 沿用 10 的快速交付策略：

- 可本地渲染时，把同版 Mermaid 生成 SVG/PNG 后嵌入 PDF，不把代码块误当已渲染图片；图旁保留短标题及必要的规则/AC 引用，避免关键编号仅存在于无法文本提取的位图里。PRD 图中文字沿用 10 的黑字规则：在渲染时设为纯黑，重点可加粗或少量标红，背景保持浅色可读；不要让渲染器默认的灰色标签进入图片，因为 PDF 正文样式无法改变已嵌入图片里的字色。
- 缺少可用渲染器或图渲染失败时，保留 Mermaid 源码，在 PDF 用同义的**状态转移表**（原状态、事件/条件、结果状态）或**交互步骤表**（角色、消息、条件/结果）承接关键逻辑，并显著说明“图未渲染，已提供等价文字视图”。不把未经渲染的代码打印进 PDF 后宣称图已交付；不因默认配图而阻塞整份 PRD。
- 只修复实际出错的图，不反复安装引擎或为布局重跑整份 PDF；一次针对性修复仍失败即采用上述降级。用户明确要求必须交付图像时，源码/表格只能算部分交付，说明缺少什么能力，不把降级当满足图像要求。
- 不自动上传业务逻辑到在线编辑器或转换服务；使用公开工具不等于获得外传私有 PRD 的授权。

见[合成双图案例](../examples/mermaid-logic.md)。示例展示的是规则到图的映射，不是每个需求都必须使用的流程或默认业务规则。
