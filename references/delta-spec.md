# PRD Diff & Delta Spec — 需求演进与增量规格

用于在既有 PRD 上追加、修正、替换或撤销规则，以及比较两版 PRD。与[需求变更分析](requirement-change.md)共用基线、影响和冲突检查，不新增固定阶段，也不重复整份原 PRD。`变更分析：在原有【客户批量导入】PRD 基础上，追加【自动识别重复客户】功能` 是入口示例，不表示变更已批准、要自动合并或进入强制模式。

## 先分清本轮交付

| 用户请求 | 本轮产物与边界 |
| --- | --- |
| 比较指定的两版 PRD | 按用户指定版本做事实性 Diff，标两版来源、状态及比较方向；不把新文件自动当成已批准基线，也不为只读比较重跑价值评估 |
| 在原 PRD 上追加/修正，要求变更分析 | 紧凑的增量说明、影响与验收差异草案；不擅自生成文件、改写正式 PRD 或升主版本 |
| 明确要求 Delta PRD / 增量规格文件 | 用[Delta PRD 模板](../templates/prd-delta.md)独立交付；未批准或普通准入未满足时显著标“提议稿／待决策／不得作为实施依据”，不冒充正式实施 PRD。普通正式准入和强制范围边界仍按 10 执行 |
| 已采纳变更，并授权合并/修订完整 PRD | 再核对当前基线与冲突；只合并已批准且适用的差异，保留旧版，按 10 生成新版源稿/PDF。只请求 Delta 不自动重写完整 PRD |

Delta PRD 是已有 PRD 的补充，不能脱离其基线单独当作完整规格。无论提议稿还是正式增量文件，只要实际生成 Delta PRD，默认沿用[10 的 PDF 交付规则](10-prd-generation.md#pdf-文件交付两种模式通用)，保留可编辑源稿；用户明确只要 Markdown 等其他格式时遵从。仅聊天中的变更分析不触发 PDF。强制范围内可带普通未知项交付，不以 Delta 名义绕过安全、授权、隐私、合规或把未决内容标成已确认。

## 1. 锚定基线，而不是猜旧逻辑

- 记录需求 ID、PRD 文档/版本/来源及批准状态、相关 CR，必要时加卡片 revision。实际变更以最新可核验的已批准业务基线为准：**完整 PRD + 已批准但尚未合并的增量及其顺序**；未决、被拒或撤回的提议只参与冲突核对，不视为有效规则。仅凭版本号较大或文件较新不能认定已批准。
- 用户只要求比较指定两版时可以按指定比较，但说明与当前已批准基线的关系；不能借此覆盖较新的有效规则。尚无批准版本可用可核验草案作未批准基线。基线不全时只比较可核验部分，将缺失处标“原规则待核对”，按问答式澄清索取影响结论的版本或条款；不能宣称完成精确 Diff。
- 沿用稳定规则、FR、AC 编号；没有规则编号时，以“文档版本 + 章节/段落 + 原文片段”定位，必要时给本次差异编号 `D-01`，不静默重编号整份 PRD。FR/AC 的新增、修改、停用沿用 09 规则，停用 ID 不复用。

## 2. 按语义形成增/改/废，不按文本缺失猜业务决定

每个差异用 `D-ID → 操作 → 基线定位与原规则 → 新规则/作废后的行为 → 受影响 FR/AC → 状态与来源` 表达。按实际出现的操作列项，没有某类变化可省略；不要为凑齐三类虚构删除或功能。相同规则只完整表达一次，影响分析引用 D-ID。

| 操作 | 必须说清 |
| --- | --- |
| **作废原规则** | 精确指出拟停用的条款及适用范围、原因和采纳后由什么行为替代；若无替代，明确该行为取消及数据/流程处理。未批准标“拟作废”，不宣布旧规则或旧用例已经失效 |
| **修改原规则** | 同一意图下的旧条件/行为 → 新条件/行为，写清覆盖哪个子句、哪些条件保持不变；只改一个条件不废掉整个 FR |
| **新增规则** | 说明原文明确无此行为、或仅在已读材料中未定义，给新规则/行为编号及与现有流程的接点；明确角色、前置/输入、触发、可观察结果和适用异常，不确定处标假设或待确认 |
| **保留不变** | 引用未受影响的范围、规则、FR/AC 及仍有效的决策来源；不重抄全文。不把旧证据直接当成最新事实，有影响才重开判断 |

新稿没写某条规则、章节移位、措辞精简不自动等于业务作废。先区分明确撤销、表达变化和遗漏待核对；仅文字变化不造功能变化。新需求中没提某个基线条款，不能直接覆盖它。明确作废、修改某子句和新增替代规则同时出现时，说明替代关系，避免同一条款被互相矛盾地处理。

## 3. 增量也要足以指导研发与 QA

对变动部分形成方案后，复用需求变更分析中的合理性、依赖、现有功能及冲突检查。只展开受影响项；未获授权实查的系统影响标待核验，不能因为 Diff 很小就认定风险低。

范围变化按[联动规则](requirement-change.md#范围变更的联动更新)检查 FR、AC、指标口径/基线/目标及验收覆盖，将必要影响接入现有 D-ID、影响和 QA 表。新范围没有实测基线时标待测，旧数据保留原适用范围，不将目标改动或覆盖计划当作已达标。保留未变但需回归的条目及原因；差异表、记录和正文各自引用编号，不再生成重复的完整变更报告。

强制范围按 [06 轻量风险知情单](06-feasibility.md#强制执行轻量风险知情单)记录本次新增/受影响风险、旧接受是否仍适用及复盘条件，未变风险引用原记录。独立风险单与 Delta 使用同一 dN 修订，正文复用同版风险内容；原批准不等于新风险已接受，不借此重跑普通产品评估。

证据沿用[统一台账](evidence-ledger.md)，增量只写受影响的 `E@台账版本 → H@记录版本 → DEC@记录版本 → REQ / 指标 → SOL → FR / AC` 与 D-ID 的对应。新增、撤回、过期或范围变化的证据只重开相关判断；仍有效的基线链通过固定版本保留，不把原记录静默改写为新结论。`DEC` 是决策编号，`D-ID` 是增量差异编号。保留关键支持与反证摘要、范围及实际决定状态，不为链条完整虚构节点或批准，也不复制全部台账。强制范围只沿用真实指令/决定与已有方案风险关联，被跳过的产品假设仍标未评估。

- 每个新增/修改行为映射到 FR 和对应 AC，写明角色、前置/输入、触发、可观察结果及必要的数据副作用；不能只写“支持查重”“符合新规则”。作废条目注明旧 AC 在获批后的停用或替代去向，保留历史，不将旧 AC 立即删除。
- 列出 QA 用例需新增、更新、停用的范围，以及未变但应回归的功能/数据；复杂度决定覆盖面，不降低单条明确度。未知导致结果不可判定时标 `QA 编写受阻`、责任人及关闭条件；生成规格不代表测试通过。
- 例如“自动识别重复客户”并未确定去重字段、租户/权限范围、同文件与库内重复、识别后跳过/阻断/合并等策略。这些应来自用户/基线或作为待决方案，不能把“识别重复”扩成未经批准的自动合并、删除或跨租户查询。

## 4. 多次变更、版本与合并

Delta 文档记录自己的修订号（沿用项目规则；无规则时可用 `d1`、`d2`），与**基线 PRD 版本、拟目标 PRD 版本、CR 编号、卡片 revision**分开。提议稿不占用正式 PRD 新版本；目标未知就写待定，不能默认“生成 Delta = 主 PRD 升版”。同一 Delta 修订时在开头简述相对上一修订的变化；首份标首份，不虚构上版。

确认前复查基线是否漂移、是否已有增量满足此次诉求、是否与其他未决或已批准 CR 冲突。同一条款的多次修改须说明适用顺序和最终有效规则，不能用“最后收到的提议优先”解决冲突。重基线后保存新修订并列出差异；已批准旧增量保留追溯，新版本分析不静默改变它的内容或状态。

获准合并时仅应用已批准、适用且无未解冲突的操作，保留未变规则和有效结论。新版完整 PRD 的简短摘要仍比较紧邻上一份完整 PRD；独立 Delta 则比较其明确标注的业务基线，两种比较口径不要混用。若暂不合并，标明当前有效文档组合及已批准增量顺序，避免下一轮只读旧完整 PRD 丢掉已经采纳的变化；本轮被拒/待决内容不得混入该组合。批准不等于上线或有权改系统。

Delta 内的变更记录沿用 CR、真实来源/状态和基线→增量修订；修订时保留前次记录与历史指标口径，不把上一轮拟议内容自动写成生效规则。获准整合后，将本次已纳入的影响与记录同步到完整 PRD 的[变更影响与记录](10-prd-generation.md#变更影响与记录)，不重复登记同一变动为多个新 CR，也不改写无关 FR/AC。

变更涉及已有状态图/时序图时，按[Mermaid 逻辑图](mermaid-diagrams.md)将图 ID、受影响转移/消息与 D-ID、FR/AC 关联；只修订受影响图，拟议与生效路径分清，源图和导出图片同步到本份 Delta 的修订，不沿用旧图冒充新逻辑。

## 交付最小检查

交付前一次核对：旧规则定位可追溯；增/改/废没有扩大作用范围；不变内容未被误覆盖；差异状态与批准来源一致；受影响 FR/AC 与 QA 回归范围齐备；待决冲突没有被写成生效规则。Delta 的源稿/PDF/文件名使用同一文档修订，如 `REQ-001-Delta-CR-003-d1.md/.pdf`，正文末尾使用 `PRD-END:REQ-001-Delta-CR-003:d1`。PDF 最小检查只覆盖本份 Delta 应交付的规则与 FR/AC 编号，不要求重复装入整个基线。

保存业务 Delta 仍须在用户授权的项目目录，不能放进公开 Skill 仓库。启用需求库时在已有 `links` 引用 Delta 及基线、`analysis` 记录待决影响；只有获准采纳并更新时才按持久化规则修改正式范围与决策。分析、提案与已批准规格分别标状态，不建立相互矛盾的第二份业务事实源。
