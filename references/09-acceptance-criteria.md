# 09 Acceptance Criteria — 验收标准

## 目标与入口

在 PRD 生成前，把**已选方案的本期交付范围**逐项拆成可独立验收的功能点，再为每个 FR 定义指定场景下可观察的功能通过/不通过条件（AC），供 QA 编写测试用例、供 10 直接引用。AC 规定交付结果如何判定合格，不表示功能已经测试通过、获准开发或上线。

- **普通模式**：08 决定“实施投入”后，根据确认的范围和方案生成正式验收标准，再进入 [10 PRD 生成](10-prd-generation.md)。若仅被要求提供验收标准、但实施门槛未通过，可交付显著标明“草案／待决策”的条目；不得据此自动生成正式 PRD。
- **强制执行模式**：完成 [05 强制方案](05-solution-analysis.md#强制执行用法) 与 [06 轻量风险知情单](06-feasibility.md#强制执行轻量风险知情单)后生成验收标准，再进入 10。把已确认的风险控制映射到 FR/AC，并补齐风险单中的关联编号；未知验收条件显著标为受阻，不要求普通风险确认全部关闭才交付 PRD。只跳过产品评估门槛，不跳过安全、权限、隐私、合规和真实性要求。混合请求按需求 ID 分别处理，不将强制范围外的内容纳入验收。

## 生成方法

1. 从需求 ID、已选方案、角色、触发条件、主流程、业务规则、交付范围与非目标提取**本期功能点**。一个原始需求可拆成多个 `FR-001` 形式的稳定编号；每个 FR 只描述一个可独立判断的产品行为或规则分支，不用“完成某页面/模块”笼统代替。已有编号需保留追溯，细化时补充新编号。候选方案、未来设想或未获确认的需求不写成必验内容。
2. 对每个 FR 生成一个或多个 `AC-001` 形式的验收条目，按结果不同的场景拆开。每条写清**适用角色/权限与前置状态、输入或数据条件、操作/事件、预期可观察结果（含必要的数据或状态变化）**；QA 应能据此判断通过或失败。可用 Given / When / Then，也可用等价短句。主路径之外，仅对实际适用的失败、取消、重复、边界值、状态流转、无权限、数据可见性与完整性，以及已确认的性能、安全或合规要求补充条目；失败或拒绝操作涉及数据时，应明确预期副作用或保持原状的规则，未知则待确认。不机械凑场景数。转化、留存等价值指标不直接充当功能验收结果。
3. 每条保留 `需求 ID → FR 功能点 → AC 编号 → 场景/数据条件 → 前置条件与角色 → 触发 → 预期结果 → 规则状态`，可使用[功能点验收表](analysis-templates.md#功能点验收表09)。同一规则的共用前置条件可以引用一次；不同结果或判定口径不能藏在“正常处理”“符合预期”等模糊措辞里。QA 可以自行设计执行步骤和具体测试数据，但不得被迫猜测产品规则、权限边界、输入范围或结果口径。
4. 对照方案检查是否超出本期范围、是否遗漏功能点或关键分支、条目之间是否矛盾。没有依据的数值、默认值、错误提示、时限、容量及系统现状不得自行补造；写明“待确认”的具体决策点、责任方（未知则待指定）和影响。为方案连贯而提出的可讨论条件标“假设”，不得伪装为已确认验收阈值。若条目的适用性依赖未核实的系统现状，拆出已确定的行为，将依赖条件单列待确认；不能仅用“若存在”就把整条标为已确认。

规则状态区分**已确认／假设／待确认**。若缺失条件导致 QA 无法写出明确预期结果，另标**QA 编写受阻／验收判定待定**，说明需谁在何时关闭；不以笼统的“待确认”冒充可测。普通模式的本期关键功能点未达到 QA 可编写程度时，不宣称 09 完成或直接进入正式 PRD；强制执行可带缺口进入 PRD，但必须显著列出受阻的 FR/AC 和关闭条件，不宣称该部分已可验收。安全、权限、隐私或合规存在不可接受冲突时，先改为合规方案或明确阻断项，不以“待确认”默认放行。

## 按复杂度控制覆盖面

- **简单**：紧贴每项功能写少量主路径和真正适用的边界、权限或异常条件；避免把短 PRD 扩成测试用例全集。
- **中等或暂按中等**：补齐影响结果的多步骤流程、角色、状态、数据和主要失败路径。
- **复杂／战略或已知高影响**：按关键角色、系统边界、敏感数据、不可逆操作、迁移/回退及风险控制拆分验收；为关键联动结果明确可观察的检查点。高风险不因其他维度较低而省略。

复杂度来自[五维复杂度判断](complexity-assessment.md)，决定场景覆盖面，不降低单条标准的明确程度。完成前按 `需求 ID → 每个本期 FR → 对应 AC` 检查覆盖：没有孤立功能点；QA 无需猜测产品规则即可为每个已确认条目写出测试用例；关键约束有对应条目或明确待定项；非目标未混入。验收标准不是逐步测试脚本，不必穷举测试数据和操作步骤。进入 PRD 时复用这些条目和编号，按文档层级排版，不在验收模块和 PRD 中重复生成两套互相不同的标准；范围或方案改变时只更新受影响条目。

已有[状态图/时序图](mermaid-diagrams.md)时，核对确认的转移、消息及成功/异常分支能映射到 FR/AC；禁止转移、权限拒绝和数据保持原状也需有适用判定。不以“符合图示”替代验收条件，图中的待确认分支仍按本阶段的 QA 受阻规则处理；图文冲突先回到来源核对，不能任选一份当事实。

## 需求变更时的验收差异

收到对既有需求的变更时，先按[需求变更分析](requirement-change.md)确认基线、变更状态和波及范围。以原 `需求 ID → FR → AC` 映射为清单，逐项标为**不变 / 修改 / 停用 / 新增 / 待确认**：不变条目沿用原编号；规则变化时保留旧条目与原版本的追溯，新版本给出明确的新预期；停用条目不再作为新版本的必验项，但历史测试与决定不得抹除。检查被改动的角色、前置条件、输入边界、状态、异常、权限、数据结果及跨功能联动，指出 QA 用例、测试数据和回归范围应如何变化；实际测试是否通过仍由 QA 判定。

提议尚未采纳时只产出**验收差异草案**，不直接覆盖已批准的 AC 或宣布旧用例失效。若多次变更对同一 FR/AC 给出互斥预期，或依赖的其他需求版本未确定，列出冲突编号、影响和决策人；受影响条目保持待决，不把两个预期同时写成正式标准。强制执行的既定范围可继续形成方案及 AC，但独立新增范围仍按自身模式路由；安全、权限、隐私和合规冲突不得因变更被默认放行。

按[范围变更联动规则](requirement-change.md#范围变更的联动更新)同步维护**覆盖差异**：受影响 FR 的主路径、边界、异常、权限、数据及联动场景分别关联新增/修改/停用 AC；未改规则但因共享依赖需回归的条目列“保留回归＋原因”，其原文与编号不改。若已有 QA 用例编号则引用其需改范围，未提供不编造。删除 AC 前核对是否仍覆盖其他在期 FR；范围缩小不自动取消共享的安全或数据约束。指标范围/采集口径变化仅联动确有关系的采集、计算或展示 FR/AC，不把业务目标达成当功能通过条件。规格覆盖、QA 可编写程度与实际测试结果分别记录，不按条数声称 100% 覆盖或沿用旧版通过结果；将该差异复用到 PRD 的变更影响部分，不另生一套 AC。

若交付 [Delta PRD](delta-spec.md)，将上述差异绑定其 D-ID 与基线版本，未变 AC 通过引用保留，需回归的未变项另列；没有重新列入增量文件不代表停用。作废只针对明确条款/场景，不能因某个子句改变就使整个 FR 的所有 AC 失效。
