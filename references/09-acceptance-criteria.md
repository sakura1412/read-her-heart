# 09 Acceptance Criteria — 验收标准

## 目标与入口

在 PRD 生成前，把**已选方案的本期交付范围**转换为可观察、可测试的通过条件，供 10 直接引用。验收标准定义“交付成什么样算符合要求”，不是 07 用来判断需求是否值得投入的验证实验，也不表示功能已经测试通过、获准开发或上线。

- **普通模式**：08 决定“实施投入”后，根据确认的范围和方案生成正式验收标准，再进入 [10 PRD 生成](10-prd-generation.md)。若仅被要求提供验收标准、但实施门槛未通过，可交付显著标明“草案／待决策”的条目；不得据此自动生成正式 PRD。
- **强制执行模式**：完成 [05 强制方案](05-solution-analysis.md#强制执行用法) 后直接生成验收标准，再进入 10；只跳过产品评估门槛，不跳过安全、权限、隐私、合规和真实性要求。混合请求按需求 ID 分别处理，不将强制范围外的内容纳入验收。

## 生成方法

1. 从需求 ID、已选方案、角色、触发条件、主流程、业务规则、交付范围与非目标提取**本期可验证的产品行为**；给功能需求稳定编号（如 `FR-001`），验收条目使用对应编号（如 `AC-001`）关联。不要把候选方案、未来设想或未获确认的需求写成必验内容。
2. 为每项适用行为写清**前置条件／角色 → 操作或事件 → 可观察结果**。可用 Given / When / Then，也可用等价短句；每条应能让验收者明确判断通过或不通过。主路径之外，按实际影响覆盖失败、取消、重复、边界值、状态变化、角色权限、数据可见性与完整性，以及已确认的性能、安全或合规限制；不机械罗列无关场景。转化、留存等价值指标不直接充当功能验收结果。
3. 对照方案检查条目是否互相矛盾、是否超出范围、是否遗漏会改变交付结果的条件。没有依据的数值、默认值、错误提示、时限、容量及系统现状不得自行补造；写明“待确认”的具体决策点、责任方（未知则待指定）和其影响。为方案连贯而提出的可讨论条件标“假设”，不得伪装为已确认验收阈值。若条目的适用性依赖未核实的系统现状，拆出已确定的行为，将依赖条件单列待确认；不能仅用“若存在”就把整条标为已确认。

每条至少保留 `AC 编号 → 需求/FR 编号 → 条件与预期结果 → 状态（已确认／假设／待确认）`；来源或约束只在有助于追溯时补充。若某个待确认项使通过/不通过无法判定，标记为**验收判定待定**并指出需谁在实施或验收前确定；强制执行可带此缺口进入 PRD，但不得声称该条已可验收。安全、权限、隐私或合规要求若存在不可接受冲突，先改为合规方案或明确阻断项，不以“待确认”默认放行。

## 按复杂度控制覆盖面

- **简单**：紧贴每项功能写少量主路径和真正适用的边界、权限或异常条件；避免把短 PRD 扩成测试用例全集。
- **中等或暂按中等**：补齐影响结果的多步骤流程、角色、状态、数据和主要失败路径。
- **复杂／战略或已知高影响**：按关键角色、系统边界、敏感数据、不可逆操作、迁移/回退及风险控制拆分验收；为关键联动结果明确可观察的检查点。高风险不因其他维度较低而省略。

复杂度来自[五维复杂度判断](complexity-assessment.md)，决定条目详略，不替代逐项适用性判断。完成后核对：本期每个功能需求有可追溯的验收结果，关键约束有对应条目或明确待定项，非目标未混入。进入 PRD 时复用这些条目和编号，按文档层级排版，不在验收模块和 PRD 中重复生成两套互相不同的标准；范围或方案改变时只更新受影响条目。
