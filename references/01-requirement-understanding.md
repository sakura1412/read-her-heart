# 01 Requirement Understanding — 需求理解

## 目标

把原始表达转换为可独立决策、可追溯的需求，不在这一阶段判断“做不做”。需求可能同时包含现象、目标、方案和来源；先拆开再分析。

一次输入多条独立需求或要求维护 backlog 时，先按[批量需求入池](requirement-pool.md)保留原始条目、拆分/关联重复项、稳定 ID 与分析批次；本阶段承接选中批次的条目做逐项理解，不因入池就为全部候选展开完整七层或逐项追问。项目形态按项目组确认，未知时不阻碍分支无关的入池整理。

## 工作步骤

1. 首先确认项目形态：**“这个需求是在已有系统中修改，还是从 0 到 1 创建新系统？”** 用户已说明或上下文可确定时直接记录，不重复询问；未说明时先问，不默认要求系统地址或登录。若是新系统替换或对接旧系统，记录新建目标与既有依赖的边界。
2. 原样保留用户诉求，并分离：现象、问题猜测、目标、候选方案、来源/驱动、期望决策。
3. 识别目标用户、使用场景、触发时机、当前行为或替代路径、期望结果和明确的非目标。0→1 项目的“当前”指现有业务/人工做法、用户替代方案或尚无解决方式，不虚构目标系统的页面、能力或数据；已有系统改造才区分已核实与未核实的系统现状。
4. 将可独立取舍、验证或上线的事项拆成原子需求，分配或复用稳定的需求 ID；按 ID 记录模式及范围。同一需求的范围内细化继承已有模式，新需求默认普通评估；涉及强制、混合或范围变更时按 [作用范围与继承](mandatory-execution.md#作用范围与继承) 路由。
5. 采用“双轴分类”：一个主类型、零到多个关联类型、一个或多个来源标签。类型混合或不明确时读取 [需求分类与分析路由](requirement-classification.md)。
6. 标记每条信息为已知事实、合理假设或待验证，并注明来源和时间范围。
7. 在以上最小整理后、深入分析前，读取 [五维复杂度判断](complexity-assessment.md)，按“业务影响 × 系统影响 × 用户影响 × 数据风险 × 不可逆性”逐维记录等级、依据与未知项，再确定简单 / 中等复杂 / 复杂或战略的分析深度及方法上限。未知时给出待确认项和临时档位，不能先完整分析再补写复杂度。

像“增加一个页面”“需要 Redis”“接入 AI”默认是候选方案，不是已经成立的问题。领导指定、客户强诉求、合同承诺或竞品已有是来源信号，不替代问题和价值证据。

## 退出条件

项目形态已确认，且需求已拆分、问题与方案不再混写、用户/场景和期望决策足够明确，并已记录五维复杂度及分析档位（可暂定）后，按该深度进入下一阶段。用户未回答项目形态问题时先问并将 01 记为“有条件通过”；普通模式仅可做需求拆分、证据标注及临时复杂度等分支无关整理，不启动 02 或对系统现状下结论。最初的“请分析”不视为跳过此问题；用户在被问后明确要求先给初步分析，或强制模式下要求继续交付时，才可带“项目形态待确认”输出条件化方案与缺口，不虚构现状或把未确认分支写成事实。其他信息不足时只提出最能改变判断的问题，已有系统且必要时才通过获准的 02 实查补齐系统维度，不为定级重跑完整评估。
