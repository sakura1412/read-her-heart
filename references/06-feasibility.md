# 06 Feasibility — 可行性

## 按模式选择路径

- **普通模式**：按下方六个层面判断可行性，满足普通退出条件后进入 07。
- **强制执行模式**：05 方案后只走本文件的[轻量风险知情单](#强制执行轻量风险知情单)，然后进入 09 验收与 10 PRD；不恢复问题、价值、证据或优先级门槛，也不要求完成普通模式的全套可行性评审。

## 普通模式目标

判断推荐候选能否以可接受的依赖、成本和风险落地。技术上能实现不等于整体可行。

## 六个层面

| 层面 | 必查内容 |
| --- | --- |
| 产品/流程 | 角色、流程、业务规则、异常、范围与采用成本 |
| 界面交互 | 入口、状态、反馈、一致性、可访问性与复杂任务负担 |
| 技术 | 架构依赖、性能、可靠性、迁移、兼容、测试、运维与技术债 |
| 数据 | 来源、口径、质量、权限、保留、迁移、追踪与可观测性 |
| 运营组织 | 配置、内容、审核、客服、培训、SOP、跨团队责任和长期维护 |
| 安全合规 | 隐私、安全、审计、地域/行业规则、合同与残余风险 |

系统界面观察只能支持产品/流程和部分交互判断。后端架构、API、数据模型、并发、迁移、安全设计和真实研发工作量需要代码、技术文档、预研或研发负责人确认。

## 估算规则

- 没有研发输入时，Effort 写“待研发确认”，不自行估算人日、人周或工期。
- 没有运营、法务、安全或数据负责人依据时，相应成本和风险写“待确认”。
- 可以指出工作项和依赖，但不能把工作项数量自动换算为确定成本。

## 产物

记录各层面的结论（可行 / 有条件可行 / 不可行 / 待确认）、依据、依赖、风险、责任方和确认方式。默认合并成一张简表；仅复杂风险需要独立登记表时，详细记录发生条件、影响、缓解措施、残余风险和可逆性，矩阵中只引用风险编号。聊天只提影响决策的约束、重大风险和待确认项。

复杂/不可逆范围在进入08前还需[事前验尸与反方评审](premortem-review.md)。本阶段提供实际方案、风险与回退依据；评审新增发现回填本记录或对应阶段，不维护第二套风险清单。风险已明确不可接受时立即限制受影响范围，不等待评审。

## 普通模式退出条件

风险可接受或有明确的消除条件时进入 07。存在不可接受的安全、隐私、法律或合规风险时不得进入实施投入或正式 PRD；风险未知且可能改变决策时必须验证或评审。

## 强制执行：轻量风险知情单

把 05 已发现的约束和未知项整理成一份可追溯记录，而不是重新回答“该不该做”。使用[风险知情单模板](../templates/risk-acknowledgement.md)；简单需求可压缩为短说明和少量条目，不强制风险矩阵、打分、签字流程或额外评审会议。

高复杂/不可逆的强制范围，在本节内做[事前验尸与反方复核](premortem-review.md#强制执行与轻量交付)：假设方案失败，倒推安全、依赖及回退问题，再以另一视角挑战控制措施；重要发现与处置并入下方风险记录，标实际评审方式与局限。只审如何交付，不重开值不值得做，不转回07/08；普通未知或缺独立评审人不阻塞带标注的PRD，底线风险照常调整/阻断。

### 记录内容

1. **身份与范围**：知情单 ID、需求 ID、方案/PRD 版本、日期、强制指令与适用/排除范围；混合请求仅覆盖强制项。
2. **被跳过的评估**：03 问题、04 价值、07 决策验证/证据、08 优先级标“由强制指令跳过／未评估”，不是已通过。06 只做轻量风险记录，完整可行性评审未做的部分如实列明；已有有效结论可引用其来源和范围，不抹除历史。
3. **已知风险与已知的未知项**：逐条使用稳定 `RISK-001` 编号，记录依据/信息来源、可能后果、影响范围与对应 SOL/FR/AC（09 尚未编号时先关联方案，之后补齐）。未知不等于低风险；无依据不填写概率、损失金额、研发工期或可行性结论。
4. **决策与接受前提**：分别记录“必须做”的决策来源和具体风险的接受决策人、权限范围、确认来源/时间、接受范围与前提。风险处置责任方可以不同，未知写待指定。逐项区分“待确认 / 已接受限定风险 / 附条件接受（条件未闭） / 不接受或不可豁免”；不把名义负责人当成已确认的决策人。
5. **缓解、关闭与复盘**：记录适用的缓解措施、前提关闭方式/节点及责任方；列明触发复盘的事件、触发后的动作和责任方。例如范围或数据边界变化、依赖失效、确认结果推翻假设、事故发生或接受前提不再成立。未提供的日期/阈值写待确认，提出的阈值标建议；不编造强制数字。说明哪些触发只需复核，哪些要求限制或暂停受影响实施/发布。

### 真实性与边界

- “必须做”、领导拍板、收到知情单、沉默或预选选项都不等于具体风险已被接受。没有明确确认时保持待确认；已有明确且有范围的确认可直接记录，不重复索要。知情单记录责任与决定的来源，不替组织分配法律责任。
- 允许明确接受**限定范围的不确定性**，但不能把未知写成已消除、可行性已证实或验收已通过。附条件接受且前提未闭时不能写“无条件放行”。
- 缺少普通风险确认、决策人、技术估算或价值证据，不阻塞方案、09 和 PRD 交付；将缺口、影响和需要谁在何节点确认写入产物。**文档可交付不等于获准实施/上线**，不自动发起签字、通知、监控或排期。
- 安全、权限、隐私或合规的不可接受冲突不能靠风险签收豁免。调整为满足同一目标的安全方案；不能消除时明确阻断受影响范围，未受影响的安全部分可继续，不把危险部分写成可执行指令。相关未知项也不得默认为已获授权或合规，明确实施/发布前的核实条件。

### 交付与变更

生成强制 PRD 时，默认在同一授权输出目录交付一份独立 Markdown 风险知情单，并将**同版同内容**作为 PRD 的专门风险章节纳入源稿及 PDF；同一内容复用，不重新写第二套风险表。默认不另导出风险单 PDF。用户明确指定其他格式时遵从；仅要求阶段分析时先给紧凑记录，不擅自创建业务文件或 PRD。

风险单随所关联 PRD 版本或 Delta 修订号标识；修订时保留旧版、风险 ID 和确认来源，正文其他位置引用 ID 不重复铺陈。Delta 只记录本次受影响/新增风险并引用仍适用的旧记录。范围、方案、数据、依赖或接受前提改变时，只重审受影响的接受结论；旧确认不能自动覆盖新风险、新范围或已失效前提，需重新确认的条目标明待决。未批准变更保留提议状态，不覆盖有效风险记录；仅同内容重导出不制造新确认或版本。

完成记录即可进入 [09 验收标准](09-acceptance-criteria.md)，把已确定的风险控制映射到对应 FR/AC，不能确定的验收条件标为受阻。再由 [10 PRD 生成](10-prd-generation.md)交付；不转回 07/08，也不把风险知情单写成可行性已通过的证明。
