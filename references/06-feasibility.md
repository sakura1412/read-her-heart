# 06 Feasibility — 可行性

## 目标

判断推荐候选能否以可接受的依赖、成本和风险落地。技术上能实现不等于整体可行。

## 六个层面

| 层面 | 必查内容 |
| --- | --- |
| 产品/流程 | 角色、流程、业务规则、异常、范围与采用成本 |
| 界面交互 | 入口、状态、反馈、一致性、可访问性与复杂任务负担 |
| 技术 | 架构依赖、性能、可靠性、迁移、兼容、测试、运维与技术债 |
| 数据 | 来源、口径、质量、权限、保留、迁移、追踪与可观测性 |
| 运营组织 | 配置、内容、审核、客服、培训、SOP、跨团队责任和长期维护 |
| 安全合规 | 隐私、安全、审计、地域/行业规则、合同与残余风险 |

系统界面观察只能支持产品/流程和部分交互判断。后端架构、API、数据模型、并发、迁移、安全设计和真实研发工作量需要代码、技术文档、预研或研发负责人确认。

## 估算规则

- 没有研发输入时，Effort 写“待研发确认”，不自行估算人日、人周或工期。
- 没有运营、法务、安全或数据负责人依据时，相应成本和风险写“待确认”。
- 可以指出工作项和依赖，但不能把工作项数量自动换算为确定成本。

## 产物

输出可行性矩阵：每个层面的结论（可行 / 有条件可行 / 不可行 / 待确认）、依据、依赖、风险、责任方和确认方式；另列风险登记表，包含发生条件、影响、缓解措施、残余风险和可逆性。

## 退出条件

风险可接受或有明确的消除条件时进入 07。存在不可接受的安全、隐私、法律或合规风险时不得进入实施投入或正式 PRD；风险未知且可能改变决策时必须验证或评审。
