# 需求变更分析 — 只重开受影响的判断

当用户修改**已有需求**的目标、范围、业务规则、流程、角色/权限、数据、接口或验收预期，或新材料可能推翻既有结论时使用。本路径不是第 11 个阶段：先确定变更差异，再沿 01–10 中受影响的最早判断继续；无关结论保留。文字润色或不改变行为的澄清可直接更正并注明来源，不必生成完整变更单。需要独立取舍的新目标分配新需求 ID，建立关联，不靠扩大旧 ID 或沿用旧强制模式跳过评估。

在原 PRD 上追加/修正规则，或用户要求 `PRD Diff / Delta PRD` 时，结合[增量规格](delta-spec.md)按作废、修改、新增列明语义差异，引用保留不变的内容。它承接本文件的影响/冲突检查，不再重复一份同义分析；仅比较指定文档时可止于只读 Diff，明确要增量文件时才按增量模板交付。

## 1. 固定基线，再看本次差异

- 给每次实质变更一个稳定编号，如 `REQ-001/CR-001`；记录提出者、时间、原始来源、理由、拟生效范围和状态（提议中 / 待验证 / 已批准 / 已拒绝 / 已撤回）。收到变更**不等于批准变更**。
- 以最近**已批准**的需求范围、方案、PRD 版本、`FR/AC`、指标口径与验收覆盖为业务基线；需求仍在讨论、尚无批准版本时，以最近可核验的工作草案作**未批准基线**，不得标成已批准。若有持久化卡片，同时记录当前卡片 `revision`。写清“原规则 → 新规则”，以及哪些内容不变。基线缺失时先重建能核验的最小现状，不能凭记忆断言旧规则。
- 区分澄清/纠错、原目标内调整、独立范围新增、替换/删除，以及外部约束变化。若用户无法确认批准版本，先给条件化影响分析和待确认问题，不覆盖现有交付文件。

若已有获批但未合入完整 PRD 的 Delta，基线须同时包含它们及适用顺序；不能只读旧完整 PRD。未决 Delta 不计入有效规则。两版文本中缺失某条款只算遗漏待核对，除非有明确撤销依据；未批准的作废操作标“拟作废”。

## 2. 判断是否值得接受这次改动

针对**差异**回答：为什么现在改、原问题或约束是否变化、预期改善什么、放弃什么、是否有更小的改法，以及新证据/反证是否支持。只重开真正受影响的普通模式门槛：例如扩大用户范围重看问题和价值，改交互重看方案与验收，改数据处理重看可行性和风险；不把旧批准当作新范围自动获批。成本、工期、收益未知则写待确认和责任人，不造数值。原目标内的小改动也可能因高风险而需验证或暂停。

当变更影响业务、系统、用户、数据风险或不可逆性时，更新对应的[五维复杂度](complexity-assessment.md)及分析、验收和 PRD 的必要内容覆盖；不因原需求被判简单就沿用低覆盖。同一文档复用用户已确认的 PRD 类型，可建议换型但不自动升档；尚未确认的类型按 [10](10-prd-generation.md#prd-类型由用户选择)询问。

触发[事前验尸与反方评审](premortem-review.md)时，核对既有 REV 的对象、候选与依据版本；方案、证据适用性、依赖、权限或回退前提实质变化，只重开受影响发现，保留仍有效的结论与未闭异议。早期验证评审不能覆盖后续实施。新增反方意见先记为异议/假设，不自动成为新证据或获批变更；强制范围只在 06 更新方案/安全控制，不恢复产品价值门槛。

若变更落在已明确绑定的**强制执行**范围内，不恢复问题、价值、证据或优先级准入门槛；仍形成新方案、确认受影响验收和 PRD 版本，并检查安全、权限、隐私、合规及真实性。同步按 [06](06-feasibility.md#强制执行轻量风险知情单)更新受影响的风险知情记录：保留旧风险 ID 和确认来源，重新核对接受范围/前提，旧接受不覆盖新增风险或失效条件；未批准变更不覆盖有效风险单。可独立决策的新增目标默认普通模式，除非当前用户明确将它纳入强制指令。

## 3. 沿关系图查影响，而非只改当前页面

若变化来自新增反证、来源纠错、过期或撤回，先按[证据台账](evidence-ledger.md)保留原 E/版本及新材料，沿 E→H→DEC 反查相关需求、指标、FR/AC；不能只检查直接修改的功能。标明哪些旧结论仍有效、哪些因依据失效待复核，未知影响不写成无影响；证据修订本身不批准需求或验收变更。

围绕本次差异列出“受影响 / 无影响的已核验依据 / 待核验”及负责人：

1. **本需求**：目标、范围、流程、角色、业务规则、数据状态、异常、方案、`FR/AC`、PRD、发布/回退条件。
2. **其他需求**：按需求池或卡片中的硬交付前置、分析前置、软复用、互斥、共享资源关系，检查上下游的范围、假设、价值归属、优先级与条件化排期。若使用卡片库，不能只读当前卡的 `dependencies`：还要查看全池对该 ID 的反向引用，并读取受影响卡片的当前版本。只更新确有影响的 ID；没有依赖图时先查已知关联，不声称“没有影响”。
3. **现有功能与系统**：核对用户旅程、入口/页面、权限、旧数据与迁移、接口/集成、配置、报表、运营流程及兼容/回退。已有系统的事实优先来自获授权实查、受控文档或负责人确认；未实查则标“推测影响／待系统负责人核验”。0→1 无现网功能时检查已定设计与外部依赖，不虚构既有行为。

若影响落到别的需求，仅记录该 ID 的待重评项和责任人；不替它自动做投入决定、修改其正式 PRD 或宣布实施顺序。安全、隐私或合规的不可接受冲突必须调整方案或显式阻断受影响范围。

### 范围变更的联动更新

PRD 已生成后，按 **CR / 范围差异 → 受影响 FR → AC → 指标 → 验收覆盖与回归** 建立本次影响映射，连同共享规则、上下游依赖和适用风险检查。这是可多对多的关联检查，不要求每个功能都独占指标，也不表示每类对象都必须修改。各类标明“受影响 / 已核验不变及依据 / 待核验”；没有映射或资料不足时写缺口，不把查不到当无影响。

| 联动对象 | 核对与更新内容 |
| --- | --- |
| 范围与 FR | 角色、人群、地区、批次、数据边界和非目标的原值→新值；定位实际改变的条件或分支，连带查依赖同一规则的其他 FR。保留其余有效原文与稳定编号，不为局部改动重编号全文。 |
| AC | 根据变动后的 FR 更新前置、输入、边界、结果和适用异常；同一可测试意图沿用 ID 并保留旧版本，新增独立场景给新 ID，停用 ID 不复用。不能只改 FR 标题而留着旧 AC 条件。 |
| 指标 | 复用原指标编号或“名称＋口径版本”（新建可用 `MET-001`），核对适用人群、分子/分母、统计窗口、数据来源/采集、基线和目标。范围或口径变化时说明新旧是否可比；原历史基线及实测结果保留原口径，新范围无数据标待测，不按比例外推、覆盖旧值或凭范围缩小降低既定成功标准。新目标须有决定来源，目标不等于已实现效果。原未设指标且本次不涉及价值衡量时说明不适用，不为变更强造 KPI。 |
| 验收覆盖 | 逐受影响 FR 检查适用主路径、边界、异常、角色/权限、数据副作用及跨功能联动，映射 AC 的新增/修改/停用；标清未变但需回归的条目及原因。覆盖缺口写具体场景、责任方和关闭点，不以 AC 数量或“全部覆盖”代替核对。 |
| 关联产物 | 仅联动受影响的方案/图、风险、依赖、07 判据或采集计划、QA 用例引用及交付说明；若只改变价值指标，不自动改无关的功能 AC。其他需求可记录受影响提示，未获授权不修订其正式文档。 |

先核对已知关联及反向依赖，再在有依据的不变边界停止扩展；“局部更新”不能省略共享规则带来的连带影响，也不要求重跑全项目。明确区分**需改的内容**与**需回归但规则不变的内容**。批准后用同一 CR 将已确认变动写回对应段落和映射；只分析或尚未批准时，输出拟更新清单，保持有效基线不变。无法确定的指标或依赖仅标记其影响，不凭空改其他对象来制造链条完整。

更新后核对：受影响的在期 FR 均有可判定 AC 或显式阻塞，停用/新增的去向可追溯；指标的范围、口径与目标来源一致，未把旧数据标成新范围已达标；未变内容未被误改。验收覆盖是规格/用例设计状态，不是执行结果，旧版已通过的测试不能自动成为新版通过证明。此检查并入本次内容核对，不新增全篇评估或 PDF 检查轮次。

## 4. 给 QA 一份可执行的验收差异

以基线 `需求 ID → FR → AC` 逐条标记**不变 / 修改 / 停用 / 新增 / 待确认**，保留原编号与旧版本追溯：同一可测试意图的预期变化可沿用 ID 并标新版本；独立新行为给新 ID；停用 ID 不复用。对修改或新增项写清角色、前置/数据条件、触发、可观察结果，以及必要的失败、边界、权限、数据副作用与联动检查。指出 QA 用例、测试数据、回归范围和发布阻断条件的变化；测试是否通过只能由实际执行结果证明。细则按[09 验收标准](09-acceptance-criteria.md)。

提议未批准时只形成**验收差异草案**，不覆盖当前正式 AC。若关键结果口径待确认，标 `QA 编写受阻／验收判定待定`、具体问题和决策人；不能同时把互斥结果列为正式通过条件。

## 5. 每次变更都复查冲突与版本漂移

将 `CR` 与**最新已批准基线**、所有未决 `CR`，以及仍影响当前规则的历史已批准/已拒绝变更比较。至少查：同一 FR/AC、字段或流程给出互斥预期；范围、角色、权限或数据口径不兼容；依赖环或另一需求的硬前置被破坏；新旧方案/迁移与回退相互抵触；一项已撤回的假设被再次当作已确认。记录冲突双方 ID、相斥规则、受影响功能/需求/验收、证据状态、解决负责人和可选处理（取舍、拆分、改条件、重新验证）；不自动合并、不静默覆盖。

第二次及后续变更即使只改一个字段，也要重查未决冲突。若审批前基线或卡片修订已变化，先重读、重算影响与 AC 差异，再决定是否批准；旧分析不能直接套到新版本。未解决冲突仅阻断其影响的审批、正式 PRD/验收定稿或实施承诺，不无故冻结无关的已批准范围。

## 6. 决策、更新与精简交付

本次出口可为**接受 / 附条件接受或先验证 / 拒绝 / 延后 / 拆成新需求**。注明理由、适用范围、决策人、待确认项、受影响阶段与关闭条件；“先验证”需说明哪条证据会改变决定。附条件接受在关闭条件前仍是待决，不自动更新已批准基线。获批准后才更新正式方案、AC、PRD/PDF 和卡片的业务范围/依赖，保留旧版及 `CR` 链接。未批准保持业务基线不变；不把建议写成用户已同意。

批准的变更需要生成新版 PRD 时，按[10 的文档版本规则](10-prd-generation.md#文档版本与本版变更)对照**紧邻上一份 PRD**，在版本信息后简述本版实际变化，并在正文的[变更影响与记录](10-prd-generation.md#变更影响与记录)中写入本次必要联动及简短 CR 记录。受影响规则仍只在各自章节完整定义一次；未决提议不混入已纳入摘要，历史只保留索引，不复制整份报告。源稿按差异更新，仍保留未变正文；若交付完整新版 PDF，重新导出同版全文，不把“局部更新”误作仅交付几个替换页。只重导出同一内容的 PDF 时不新增 PRD 版本。

用户只要 Delta PRD 时，不默认重写完整 PRD；提议稿独立标状态、业务基线及自身修订号，不能凭生成文件更新已批准基线。正式增量仍检查适用的 PRD 准入和批准来源，文件详略只覆盖本次差异，交付规则见[增量规格](delta-spec.md)。

若项目已启用[需求状态持久化](requirement-state.md)，把 `CR` 分析/决策记录保存在**用户授权的项目数据目录**，以 [变更记录模板](../templates/change-record.md) 起稿；即使仍待决，也可在获准保存时让卡片 `links` 引用该记录、`analysis` 留简要受影响项，但不改已批准的 `scope`/`priority`。新编号须查已有链接与记录，避免重复；CR 记录从提议到决定发生实质变化时保存新版本或使用用户已有版本控制，不直接抹掉旧分析。`decisions` 只追加真实决定并保留旧修订；JSON 卡片仍是当前范围/状态的事实源，Markdown 变更记录是审计材料，不是并行编辑的第二张卡。更新前使用 `--expected-revision`，冲突时重读再合并；脚本不会自动核验链接、识别语义冲突或跨多张卡片原子更新，涉及多卡时逐张核对实际结果。未启用持久化时可在当前回复给出变更分析，但不得声称下次自动记得。不得把真实业务变更单写入公开 Skill 仓库，或保存凭证与不必要的个人信息。

聊天默认只交付**差异、合理性、受影响 ID/功能、指标与验收覆盖变化、冲突警报、决定/下一步**；复杂改动才附完整影响表。不要重述整份原 PRD 或重跑十阶段报告。用户仅询问影响时止于分析；不因一次变更自动生成 PRD、修改系统、发布或安排提醒。若用户明确要求持续监控或定时提醒，再另行请求相应授权与机制。
