# 需求状态持久化与 Backlog

仅当用户要求跨会话接续、保存分析记录或管理多条需求时使用。本模块是需求池与十阶段工作的**记录层**，不是新的产品准入阶段；一次性评估不用自动建库。保存、读取和生成视图用 [`scripts/backlog.py`](../scripts/backlog.py)，卡片字段见[JSON 模板](../templates/requirement-card.json)。

## 目录与事实边界

- 先取得用户指定或同意的**项目专用、可写、绝对路径**。一项目一目录；需求库和待保存的卡片草稿都放在公开 Skill 仓库、Skill 安装目录之外的受控位置，脚本会拒绝从 Skill 目录读取待保存草稿。没有目录时可先给卡片草稿或分析结论，但不得说“已保存、下次会记得”。
- 保存还需本次会话具有 Python、执行能力及目标写权限。缺失时继续给分析或卡片草稿并明确“尚未持久化”；能读取时可核对旧记录，不能绕过配套脚本的修订/并发保护手写保存结果。脚本成功后读取目标记录核对 ID、修订与本次变化，才声明保存完成；失败时先核实是否有部分写入，不盲目重复提交。
- 跨会话接续依赖后来会话再次提供**同一个绝对路径**，或项目上下文明确绑定该路径；聊天上下文不是持久存储。此功能不会自动迁移过去的对话、PRD 或需求池文件。
- JSON 卡片是当前需求范围/生命周期的唯一可写事实源；`show/list --format markdown` 只是从 JSON 生成的只读视图，不要把 Markdown Backlog 和卡片当两份独立记录编辑。证据材料及适用性由下述统一台账维护，卡片只引用；所有新证据仍须区分事实、假设、待确认，不因写入文件就变成已证实。
- 文件可能包含敏感业务信息。最小化保存，优先写材料标识、受控位置和摘要，不保存密码、令牌、验证码、Cookie、个人敏感信息或不必要的原始客户数据。脚本的敏感字段名校验不能代替人工检查正文。除非用户另行授权，不上传或提交项目数据目录到 GitHub。

## 卡片最小契约

每个可独立取舍的原子需求使用一个稳定 `id`，对应一张 `cards/<ID>.json`。保存前按当前证据填写；缺失保留空值/空数组，不编造。核心字段：

| 字段 | 使用规则 |
| --- | --- |
| `schema_version`, `id`, `title`, `project`, `scope` | 版本固定为 `1`；标题短而可辨；范围变化要留痕，不沿用 ID 掩盖独立新增需求。 |
| `mode` | `normal` 或 `mandatory`；只有当前用户对该 ID 与范围明确下达强制指令才设为 `mandatory`，不从材料引述推断。 |
| `status` | `评估中 / 验证中 / 实施中 / 已暂停` 是**生命周期进度**，不是价值或准入结论。“实施中”须有真实实施依据，PRD 已生成不等于实施中。 |
| `priority` | 未确定写 `null`；只有 08 的实施优先级排序或用户提供且注明来源的既有排序才能填写，验证资源次序、分析批次、紧急信号和状态不能自动转成开发优先级。 |
| `dependencies` | 每项写关联 `id`、`type`、`confirmation`、`basis`。`analysis_prerequisite`/`delivery_prerequisite` 表示当前项分别在分析/交付上依赖该 ID；`soft`、`conflict`、`shared_resource` 是关联，不强造方向。未确认关系标 `pending`。 |
| `decisions` | 按 `at` 时间顺序保留 `at`、`outcome`、`reason`、`source_refs`；更新时只能追加，不能删除或改写旧判断。最近一条是 Backlog 的“最近决策”。模式变更、投入判断和暂停/重开都要能追溯，不能把强制项写成已通过 08。 |
| `next_action`, `source_refs` | 写最小下一步与来源标识；引用字符串尽量含**材料标识、形成日期、覆盖范围/版本与可核验位置**，如 `2026-10-20｜客服工单 1–15｜受控报告路径`。空缺如实留空或标待确认，不塞入凭证或整份敏感材料。脚本不判断来源是否可信或仍有效。 |
| `analysis_batch`, `links`, `analysis` | 可选：分别记录分析批次、受控产物位置、阶段摘要。`analysis` 可存分诊时间/来源、档位/依据、重开条件与归并关联；分诊是分析记录，不自动改变生命周期或正式优先级，也不代替证据正文或 PRD。 |

`revision`、`updated_at` 和变更历史由脚本维护；每次成功更新前，旧版保存为 `<项目目录>/revisions/<ID>/rev-<N>.json`，最新版仍在 `cards/<ID>.json`。快照用于审计与恢复旧范围、来源及依赖，不参与当前 Backlog，也不能覆盖已有的不同内容。卡片不是需求全文或测试用例容器，较长的决策记录、验证 Brief、方案与 PRD 用受控文件保存，在 `links` 中引用即可。

验证使用[07 的有界 Brief](07-validation.md#有界验证启动续轮与停止)记录稳定假设/计划 ID、预算、截止、轮次、已耗及已承诺额度和每轮结果；卡片 `links` 引用原记录，`decisions` 追加真实的08投入/停止/续验决定。跨会话先加载累计历史，不能把新会话当首轮；历史不全标待核对，不当零。仅完成设计或预算待决不声称验证已启动。无需为此扩展卡片 schema 或维护第二份累计台账。

证据按[统一台账](evidence-ledger.md)在同一已授权项目目录保存一份可版本定位的记录。`links` 指向指定版台账、假设/Brief 和决策记录；`source_refs` 可引用 `E-001@台账v2｜受控位置`，可选 `analysis` 只存 E/H/DEC 索引和待复核摘要，不复制可编辑证据正文，也不增加必填 schema。跨会话须打开引用的记录，核对新材料、撤回/过期、范围与版本变化；脚本不会验证链接或自动检测证据冲突。更新台账保留旧快照，旧 PRD/DEC 不随最新同号 E 静默改变；新材料触发复核不等于自动改生命周期、批准范围或优先级。

## 保存、接续与查看

已执行的[条件评审](premortem-review.md)可通过 `links` 引用 `REV@版本`，复用同一记录中的发现、处置与未闭条件；卡片不复制整份辩论，也不增加必填字段。接续时核对对象是验证还是实施，以及范围/候选/证据是否仍适用；评审完成不等于实施批准，不自动更新状态或优先级。无新变化复用原记录，有实质变化只重开受影响发现。

先定位本次加载的 `SKILL.md` 所在目录，使用其中 `scripts/backlog.py` 的**绝对路径**；不从业务 cwd 或宿主名称猜安装目录。`--root` 始终指向**仓库外**的项目数据目录。下例中的 Python 命令按实际可用解释器选用 `python3`、`python` 或 Windows 的 `py -3`，脚本与数据路径均按当前 shell 正确引用；具体示例见 [README](../README.md#跨会话需求库与-backlog)。

1. 首次使用 `python3 "/实际/Skill目录/scripts/backlog.py" --root "/绝对/项目目录" init --project "项目名"` 建库；路径是占位示例，应替换为当前环境真实路径，只对用户选定的新目录或空目录初始化。目录与项目名绑定，后续卡片的 `project` 必须完全一致。一次性粗筛的 Markdown 需求池不自动转成卡片。
2. 用[卡片模板](../templates/requirement-card.json)准备 JSON，再执行 `save --input <卡片路径>`。新卡片若直接设为强制模式、验证中/实施中/已暂停，或填写正式优先级，须附一条有真实来源引用的初始决策。更新时先 `show --id <ID> --format json` 读取当前 `revision` 和历史，保留旧决策并按时间追加新判断；调用 `save --input <卡片路径> --expected-revision <当前修订号> --note <本次变更说明>`。`mode`、`status`、`scope` 或 `priority` 变化必须新增至少一条 `source_refs` 非空的决策；其他字段变化仍需 `--note`，但不强制虚构正式决策。没有业务字段变化时无需生成空版本；修订或快照冲突先重读、合并，不盲目覆盖。
3. 新会话先 `show` 对应 ID，核对 `updated_at`、范围、来源日期、依赖、证据时效和外部现状。省略 `--revision` 读取最新版；审计旧决策时可用 `show --id <ID> --revision <N> --format json|markdown` 读取对应快照，旧版只供比较与恢复依据，不能当作当前状态直接回写。旧卡片是**上次判断**，不是当前事实；只重开受新证据影响的最早阶段，复用仍有效的结论。模式和范围按用户当前指令及历史记录核对，不让旧强制模式扩散到新需求。
4. `list --format markdown` 给紧凑 Backlog，展示 ID/标题、生命周期状态、优先级、依赖、最近决策、更新时间、下一步；需要程序化读取时用 `list --format json`。Backlog 是视图，不从状态推断投资批准、交付承诺或已经上线。

需求归并/拆分时保留原 ID 与来源，在相关卡片决策或关联中说明，不直接改写成“从未存在”。依赖或优先级改变时检查受影响项；没有团队容量、研发估算或确认的交付前置，就只给条件化排期假设。需要按二三十条先粗筛时仍按[需求池流程](requirement-pool.md)分批，不因有文件库就让每项跑完整七层。

## 多次需求变更的记录

需求变更先按[变更分析](requirement-change.md)区分**提议、待决与已采纳**，不能把卡片 `revision` 增加或当前 `scope` 当作业务批准。获准在项目私有目录保存时，每次变更用独立 `CR` 编号和[变更记录模板](../templates/change-record.md)留下基线、前后规则、影响、冲突、验收差异与决定；在需求卡 `links` 中以 `CR-编号` 指向受控记录位置。可在 `analysis.change_control` 保留轻量索引：已批准业务基线的来源/版本、未决 CR ID 列表及最近核对时间；它只是导航缓存，仍须打开对应决策和 CR 记录核实，脚本不验证其正确性。后续会话先从最新卡片及其链接加载同一需求和受影响关联需求的已采纳、未决变更，再与当前提议比较；只看最后一条决策或最后一份 PRD 不足以发现并行冲突。卡片的 `decisions` 继续记录有来源的采纳、驳回或暂停判断；不要把未决提议覆盖进已接受的 `scope` 或正式优先级。

只有用户授权保存或更新项目业务资料时才写盘；仅评估时交付变更分析草案。采纳后以最新 `revision` 做并发校验，按受影响范围更新卡片和依赖，保留旧版快照；PRD/AC 等较长产物保留独立版本并在 `links` 引用。并发修订冲突要先重读、比较和协调，不能以旧草稿直接覆盖。脚本保留文件修订历史，但不会自动检测语义冲突，仍需按变更分析检查规则、范围、依赖与验收预期。
