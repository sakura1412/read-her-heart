# 03 Problem Analysis — 问题分析

## 目标

回答七层决策的第 1 层：**是不是真的有问题？** 区分抱怨、症状、根因、目标和候选方案。

## 分析步骤

1. 写问题陈述：哪类用户在什么场景下尝试完成什么任务，遇到什么障碍，造成什么可观察后果。
2. 检查发生频率、严重度、持续时间、影响范围、当前应对方式和不发生问题的反例。
3. 判断是功能缺口、体验摩擦、流程问题、规则约束、技术故障、认知不足还是其他原因。
4. 根因不清且会改变方案时才使用 5 Whys；找到有证据、可采取行动的原因后停止，不为凑五层继续追问。
5. 对“Bug”确认预期依据和复现条件；对强烈反馈检查其代表性；对领导指令区分目标、方案与不可讨论的组织决定。

## 问题证据卡

目标用户、真实任务或现用替代缺证时，可按[市场与用户研究](market-user-research.md#用户画像或-jtbd证据驱动不写虚构人物故事)补充任务理解与最小取证：优先最近实际行为、补救方式及反例，不把喜好、模拟用户、竞品功能或少数受访者意见直接外推为普遍问题。必要研究复用07，不要求0→1先有系统数据。

本卡是判断摘要，材料来源、时间、偏差与有效状态统一在[证据台账](evidence-ledger.md)记录；支持与反证引用同版 E，根因等关键假设沿用稳定 H。没有材料只写缺口，不能把推断补成证据。

| 项目 | 内容 |
| --- | --- |
| 问题陈述 | 用户＋场景＋任务＋障碍＋结果 |
| 支持证据 | E@台账版本；一句与当前命题相关的发现 |
| 反证/不利信号 | E@台账版本及适用范围；未查到不自动算反证 |
| 根因假设 | H 编号、根因、关联 E、可证伪方式 |
| 影响范围 | 已知范围与无法外推的边界 |
| 阶段判断 | 成立 / 部分成立 / 不成立 / 待验证 |
| 置信度 | 高 / 中 / 低及理由 |

## 退出条件

- **成立/部分成立**：带着明确问题和根因假设进入 04。
- **待验证**：进入 07 设计问题验证，不能直接进入实施投入。
- **不成立**：停止价值与方案论证，记录暂停原因和允许重开的新证据。
