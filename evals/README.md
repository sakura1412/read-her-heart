# 回归评测集

`cases.jsonl` 每行是一个独立测试：`turns` 为单会话输入；带 `sessions` 的用例须按数组顺序在**不同的新会话**运行，只共享测试目录中的文件，不共享聊天历史。`setup` 是评测准备条件，`expected` 是应观察到的行为，`forbidden` 是不得发生的行为，`failure_example` 是**合成的典型错误输出**，不是实际运行记录。`examples/normal-end-to-end.md` 则是完整正向案例；其数字和结论只适用于该虚构输入，不是所有需求的标准答案。

使用方式：先确认待测环境已加载**本仓库当前待测版本**的 Skill；每个用例在新对话或隔离上下文运行，多轮用例按 `turns` 顺序发送。持久化用例把 `<BACKLOG_DIR>` 替换为本用例独占、位于公开 Skill 仓库外的临时绝对路径；`sessions` 之间保留该目录，但不给后一会话前一会话的消息。若有 `setup`，先完成它再发送输入。若需生成文件，检查真实 PDF 与源稿；不要用真实账号、生产系统或私有业务数据跑这些合成用例。逐项核对所有 `expected` 与 `forbidden`，不要靠标题、固定措辞或正则命中判通过。记录 Skill 版本、是否通过、实际输出/文件证据、失败原因；改动规则前后用同一组用例比较。

问答续接用例要在**每一轮用户输入后检查当轮响应**，确认它是否提出必要问题，再发送下一轮答案；不能把两条用户消息一次性拼成已澄清输入。若宿主提供结构化提问界面，检查两个建议选项及界面提供的“其他/自由输入”入口；无该能力时，检查文本中有两个选项和明确的“其他：自行输入”路径。选项不能被默认选中当作用户决定。未答复用例只观察已知材料范围内的进展和待决状态，不以长时间轮询来模拟等待；收到“其他”输入后应按实际内容续接受影响的最早阶段，而不是硬套原先两个选项。

最低通过要求：模式与作用范围正确；证据不足时不假装通过普通 PRD 门槛；有明确强制指令时完成方案与逐功能点 AC，PRD 类型已明确或用户明确授权代选后按相应类型交付，保留安全和真实性边界；不编造系统实查、数据、成本或监管结论。若一个用例触发了 PRD 生成，还应检查同版本可编辑源稿、真实可下载 PDF、结束标记及 FR→AC 编号，而不只看聊天里是否宣称“已生成”；用例明确只要 Markdown 等其他格式时按该要求检查，不额外要求 PDF。

PRD 类型检查以**本次交付的实际选择状态**为准：复杂度只提供建议和必要覆盖依据，不能自动替用户定档；尚未选择且未授权代选时，在实际生成入口询问简版/标准版/完整版并简述差异，不能提前阻塞纯分析或验收工作。宿主只有两个建议项时，题干仍须说明三档，明确另一档可以自由输入；预选、沉默、仅指定Markdown/PDF格式都不算类型选择。待答时可以继续类型无关的方案/AC，不输出自行定档的最终PRD或导出文件。已选类型支持同份修订沿用，不自动扩散到无关需求；明确要求Delta或仅同稿重导，不机械增加三档问答。复杂选简版不得擅自升级或删掉必要安全与逐功能点验收，简单选完整版不凑无关空章；强制模式也遵守交付选择，但不恢复价值门槛。

批量需求用例还需核对：每条原始输入有稳定 ID 和处理去向；疑似重复项保留全部来源；粗筛、正式优先级与实施批准不混为一谈；硬依赖、软依赖、冲突和待确认关系不混写，依赖环不能伪装成可执行顺序。只有排期前提充分时才能承诺日期；缺研发容量、估时或发布窗口时，允许给带条件的处理波次，不得编造日历排期。强制状态仅绑定用户明确指定的需求，不传染相邻项或依赖项。

批量分诊用例（M53–M56）另检查三个档位的**判断依据和后续范围**：直接不投入是有可靠当前范围否定依据的本轮粗筛建议，不是永久否决或已获批准；需验证仅表示关键缺口，不等于研究已批准；值得深入不是实施投入结论。五维快速画像须区分已知影响与未知，复杂度不能替代价值判断；不要求为每条跑完整框架或填七层报告。允许某档为空，不能为了凑齐三档而编造事实或把材料不足判成不投入。

M53 核对 20 条原始输入的完整映射、真正重复与同名异权限的区别、单一来源重复转述不重复计证，以及单独的强制通道；本轮只分诊就不展开分析或交付 PRD。M54 检查 20 个稀疏候选不会被批量低估、假否决或变成 20 份完整验证 Brief。M55 检查要求继续但未指定数量时，本次最多深入 3 个规范化独立项，选择依据可追溯且不是机械取输入前几条；M56 检查指定 ID/数量优先，不用默认 3 项补齐。对所有条目提示已知重大风险和时限，不因未选入首批而隐藏；剩余项保留下一批条件，不默默全量续跑。分析名额不是团队 WIP、研发优先级或发布日期，分诊建议不自动改写持久化状态。本组均为只读合成评测输入，新增样本不代表已执行通过，实际运行结果须另行记录。

证据台账用例（M57–M60）检查**来源可追溯、适用范围和判断关系**，不是统计 E 编号数量。台账字段须能区分来源/位置/版本与直接或转述、类型、事件/观察及采集时间、发现和覆盖范围、相对假设的强度及依据、偏差、支持/反证关系、当前适用状态和修订。未知日期、样本或偏差不得补造；模型推断、计划中的采访与已获得观察不能混写。重复转述可保留别名/关联，但不增加独立证据或样本。强度标签不等于假设可信度，更不等于 07 自动通过。

M57 用轻量整理检验旧版本工单、重复转述与不等价的数据口径，不要求简单请求运行整套流程。M58 按台账 E 与 H/验证计划的具体版本逐项检查事前判据、独立样本和角色覆盖；即使结果看似超过比例阈值，也不能忽略质量条件、把未来计划算成证据或事后降低门槛。达到已确认轮次上限时仍能分析既有证据，但不能借补台账自动续验。

M59 检查证据撤回/更正后的影响范围和历史：旧 PRD 的 E/H/决策版本仍可定位，新提议不覆盖历史批准。追溯链保留需求、指标、FR、AC，再增加 `E → H → DEC`，允许多对多和未评估；`DEC` 是决策示例命名空间，不与 Delta 条目 `D` 混淆。只重开受影响的假设和决定，功能验收不因价值指标变化自动通过或作废。M60 检查简单强制需求可用少量引用完成追溯，被跳过的价值假设如实标未评估，不为填表恢复产品门槛、伪造验证或签收风险。卡片/PRD 引用的是台账明确版本，不是会无痕变化的“最新版”。

这四个用例均只要求对话中的台账、分析或 Markdown 片段，不应保存真实业务资料、生成 PDF、开展研究或修改系统；M59/M60 的片段不是正式发布或完整 PRD 交付。新增用例是合成评测设计，不代表已经运行通过，实际执行结果另行记录。需持久化时仍须使用已授权项目私有目录和可追溯链接，不把证据原文自动写入公开 Skill 仓库，也不因台账新增而强制扩展需求卡 schema。

事前验尸与反方评审用例（M61–M64）检查**触发范围、质疑质量和处置闭环**，不以多写一份反方表格为通过标准。普通复杂或不可逆事项应在 08 对相应投入作决定前完成条件性评审；简单请求不机械演练，批量只深入选中且触发的条目。参照 `references/premortem-review.md` 与同名模板，核对具体失败因果链、早期信号、预防/验证或止损措施、未知与责任边界，以及 E/H、方案和评审版本的关联。假定未来失败不是已发生的 E，不能为增强说服力编概率或事实；评审通过也不是预算批准。

M61 要逐条核对意见处置的实质依据，而不强求固定措辞或三种处置标签各出现一次：错误前提要被纠正，有效担忧保留，绝对化否决不应扩大到未受影响范围。未解决异议需有范围、返回环节和关闭条件，不能只罗列后搁置。输入限制本轮仅同模型复核，应明确非独立，不能冒充专家或另一代理签字。其他实际运行若获准调用独立代理，需以真实调用及审阅结果为依据；有工具不等于已使用，有另一代理也不等于具备人类专业审批权限。

M62 按两轮逐次检查：第一轮质疑的是有限取证方法、潜在误导、安全与信息价值，不要求未知产品价值先成立，不把候选预算或未知历史当已获批准/已耗为零；第二轮新方法可被实质采纳，但同一决策问题累计轮次已到，不能改名清零或自动追加。08 仍需单独判断验证成本、预算及授权，评审记录不替代止损规则或新增批准。已确认上限触发时仍可分析现有材料，不等于允许新取证。

M63 检查 20 条输入的去向与实际深入范围，同版同范围、仍适用的评审可引用复用；新增不可逆范围只重开受影响规则、风险和 AC，既不能沿用旧预览评审放行删除，也不能全面作废无变化内容。记录中的历史独立审阅不能冒充本轮新调用。M64 检查强制复杂项把评审收在 06 内，仅挑战方案、安全和回退，不恢复跳过的产品价值门槛；普通未知或缺独立评审人不阻止带标注的 PRD 草案，但明确越界的公共上传必须调整或阻断对应范围，不能靠“风险待接受”放行。

M61–M64 均使用只读合成输入；M64 仅交付 Markdown 条款草案，不要求完整 PRD 或 PDF。不得实际开展外部研究、联系评审人、上线或把材料保存进公开仓库。这四条是新增评测设计，**不代表已全部运行通过**；结构解析或静态检查通过也不等于行为通过，实际逐轮输出和执行结果须另行记录。

市场、竞品与用户研究用例（M65–M68）按[研究规则](../references/market-user-research.md)检查**取证与决策问题的对应关系**，而不是只看是否输出了画像或竞品表。M65 检查 0→1 无系统账号也能继续，少数同源访谈只能形成有边界的研究对象/假设画像或 JTBD；使用者与采购者分开，保留反例，不编造人口特征、引语、支付意愿或调研结果。新研究计划须说明什么材料会改变判断，沿用 07 有界 Brief 与 08 投入判断，不把计划当执行。

M66 核对同任务、客群、地区、版本与套餐，以及文档、营销、演示、路线图与实际观察的不同证据状态；未公开不等于没有，候选比较包含适用的手工/现有工具替代，不凭功能数量或资料多少排名。M67 对每个具体 H 检查市场证据的强/中/弱/未知及其依据，沿用统一 E 台账；权威但旧且不匹配的数据不能直接证明当前细分市场，同源转载不加独立证据，小样本兴趣不外推购买比例，行业热度与总量不能替代本产品问题或支付意愿。

M68 检查批量限选和强制边界：简单强制项只完善方案与 FR/AC，不因“竞品驱动”标签强制补研究，未选项不展开。普通研究到轮次上限后不能改名“市场扫描”清零或靠剩余预算续验；新的证据路径仍需有限投入决定，对外招募/问卷发送另需授权。四条均为只读合成材料，不执行联网、联系、注册、问卷、文件保存或 PDF 导出；新增样本与静态校验**不代表已执行行为评测通过**，实际输出另行记录。

PRD 类型由用户选择的用例（M69–M71）检查上述状态与范围，而不是仅检查提问里出现三个类型名。M69 先给验收检查请求，再单独进入PRD生成：前者不提前问类型，后者必须待选；随后用户在自由输入选择完整版，即使五维均低也尊重选择。M70 已明确选简版，不应擅自升级；重点检查跨系统迁移的权限、恢复/核对前提、失败保护和逐功能点AC未因篇幅被删去，未知不补造。M71 连续检查已选标准版、同份修订沿用、明确Delta以及无关新强制需求的待选择状态，不能把四轮一次性合并输入。三条只用聊天Markdown或问题，不生成文件/PDF；本轮新增是合成评测设计，**不代表全部行为评测已经运行通过**。

为保持既有用例原测试目的，M04/M07/M09/M14/M19/M28/M29/M34/M44/M47 仅在相应生成请求补充了用户明确选择标准版，其原有范围、未知项、模式和文件验收要求未改。M29仍测试同份PRD版本修订；M30/M43的同稿重导、Delta用例和仅章节片段的请求保持原输入，不额外插入类型选择。

持久化用例还需检查磁盘上的卡片及 Backlog，而非只看聊天声明：必须能从明确的项目目录重新加载；当前会话未写盘时不能宣称“下次还能记得”；公开 Skill 仓库不承载私有需求、凭证或敏感原文。卡片的历史判断、当前进度、正式优先级和依赖类型须分开，读到旧卡先检查证据与范围是否仍适用。遇到旧修订与磁盘新修订冲突，须先发现并协调，不静默覆盖。

需求变更用例还需检查：以最新已批准版本为基线，同时审视未决变更；区分澄清、同范围调整与可独立取舍的新增范围。结论要说明变更理由、受影响的其他需求和现有功能、FR/AC 的增改废与 QA 回归范围；遇到规则冲突或旧基线时指出具体版本、条目及待决责任方，不自动合并、覆盖或发布正式 PRD。没有授权持久化时不能声称已留下可跨会话追溯的变更记录。

PRD 局部联动用例（M72–M74）按[范围变更规则](../references/requirement-change.md)和[PRD 生成规则](../references/10-prd-generation.md)检查变更影响与记录：M72 核对已批准范围变化如何联动 FR、AC、指标口径/观察窗口与 QA 覆盖，并查共享组件的间接回归；不改无关规则或编号，不把新目标当已测基线。M73 仅分析未批准提案，冲突及口径缺口待核，不覆盖已批准正文，不把覆盖计划当测试通过。M74 必须逐轮运行，核对完整 PRD 加已批准未合并 Delta 的累积基线、未决冲突和实际纳入记录；完整新版的摘要对比紧邻完整上一版，历史指标不可被新口径静默重算或冒充可比结果。

三条均为合成、只读的聊天 Markdown 测试，不保存业务文件、不导出 PDF、不执行系统或实际测试；用户的文档类型选择已给定，以隔离本轮联动行为。新增样本与 JSONL 结构检查**不代表行为评测已经运行通过**，逐轮输出与结果另行记录。

PRD 版本用例还需核对交付文件本身：首版有版本、日期和状态，但不编造上一版；修订版的简短摘要只写相对紧邻上一版**实际纳入**的变更，未决提议不混入。Markdown、PDF 正文、文件名和结束标记的版本应一致；仅重导或修排版不构成需求修订，也不能绕过原有 PRD 门槛。

PRD Diff / Delta PRD 用例（M36–M39）检查**语义和状态**，不靠出现“增、改、废”三个词判通过：每条差异须能定位原规则或说明旧逻辑不可核验，新增行为与修改原约束要分开；遗漏条款不能自动判作废，局部修改不能吞掉未受影响规则。实际生成 Delta 文件时，检查基线来源/版本、CR、审批状态和 Delta 自身修订，不能把草案修订冒充主 PRD 升版。依赖已批准但未合入主 PRD 的 Delta 时，核对其应用顺序及累积规则；未决变更单列，不覆盖已批准链。QA 差异须落到对应 FR/AC 的可判定结果与必要回归，而不只列功能标题。

这些用例中的 `<OUTPUT_DIR>` 使用仓库外的独占临时目录；按 `setup` 准备原文，在运行前保留基线副本或哈希，运行后确认未被未授权改写。M36 特意只要 Markdown 草案，以隔离测试增量分析而非 PDF 导出；M37–M39 只要对话分析，不应产生交付文件。案例和失败输出均为合成材料，新增用例不代表已运行通过，真实执行结果须另行记录。

Mermaid 用例（M40–M43）检查图的**业务语义、范围和交付真实性**：简单变化不强制配图；状态图表示同一对象的生命周期，时序图表示角色/系统间的交互，两者的成功、拒绝和异常结果必须一致。逐条把转换/消息追溯到需求规则和 `FR/AC`，不要仅凭语法可解析或存在两个代码块判通过。待定超时、重试或权限不能画成已确认路径；当前与提议版、已批准未合并增量与未决提案不能混为一张生效图。对存在本地 Mermaid 解析/渲染能力的环境，可补一次语法检查，但渲染成功不代表产品规则正确。

M42 运行前保留基线材料与旧图的副本或哈希，检查只产生独立提议产物；M43 使用可导出 PDF、但无 Mermaid 渲染器且不允许外部服务的隔离环境，检查真实 PDF 的等价状态/交互说明、可编辑源码与明确的图片交付缺口。不能用打印的 Mermaid 代码冒充已渲染图，也不能靠宣称“导出成功”跳过文件检查。新增用例本身不表示已运行通过。

强制执行风险知情单用例（M44–M47）检查**风险留痕而非新增产品门槛**：05 方案之后必须形成 06 的轻量记录，再与 09 验收及 10 PRD 对齐。核对被跳过评估、已知风险与未知项及依据、必须做决策来源、风险接受决策人/实际确认状态、接受前提与关闭责任、复盘触发条件及处置责任；不能仅凭表格填满就判通过。技术联系人不自动等于风险接受人，“必须做”、沉默或生成文件不等于风险已接受。普通未知、缺少决策人或尚未确认风险可以带标注继续 PRD；已明确不可接受的安全、授权、隐私或合规问题仍须调整或阻断。

M45 重点核对部分接受的风险 ID、范围、条件与历史来源是否完整保留，新增范围是否重开受影响的接受判断，以及是否将“复盘条件”误写成已创建监控或提醒。M44/M47 检查独立风险知情单源稿与 PRD 的需求范围、版本、未知项和风险状态一致；M47 还应读取真实 PDF 正文中的知情内容，不能仅检查文件名或聊天声明。不默认额外输出一份风险单 PDF。M46 仅要草案分析，不应生成文件或执行真实系统动作。以上为合成回归用例，新增不表示已运行通过。

验证分工与止损用例（M48–M52）检查**设计、投入决定、实际执行**是否分开：07 的 Brief 只回答验证什么、如何取得能改变判断的信息；08 可在实施门槛尚未满足时单独评估这笔验证成本，但不能把未完成的判断记为通过。批准验证不等于批准实施或获得系统/参与者操作授权。旧用例中的“给验证方向/Brief/验证出口”也仅表示形成设计或待决建议，不能据此认定已经获批启动。

检查预算（包括适用的人力等非现金资源）、截止、轮次、累计已耗及承诺、决策来源是否真实且可追溯。任何已确认上限先到即止；未知消耗不能按零，未确认预算/日期不能靠 AI 补造。未指定轮次时可以提出最多两轮的建议，但不能写成既有批准。M49–M50 需读懂已给数值和时间之间的关系，不只检查输出里是否有“停止”一词；换 ID、会话或名称不能清零同一决策问题的历史。到期暂停也不等于假设已被否定。

M51 区分“用试点取证”的验证投入和“小范围自身门槛已成立”的受控实施；结论不足不能自动洗成实施，更不能豁免数据授权和安全风险。M52 则防止把建议上限变成永远不可调整的规则：真实的新信息路径和明确有限追加批准可以更新边界，但须保留累计历史与新的止损条件，不能滚动续费。M48–M52 本轮均只要只读建议，不应创建业务文件、发消息、开展实验或生成 PRD；这些是合成评测输入，不是已执行的测试结果。

澄清交互用例还需核对：仅在答案会改变项目形态、模式/范围、方案、权限或验收预期且上下文无法判定时提问；每次聚焦一个最关键歧义，两个选项应真实可区分且不封闭自由输入。问题待答时只推进不依赖该答案的整理，不能默认为首选或把未确定规则写成事实、QA 可测条件或普通模式实施批准。强制模式的普通信息缺口可进入带标注的方案与 PRD，不因等待普通证据而恢复被跳过的产品门槛；安全、授权和合规缺口仍按原规则处理。

## 跨宿主检查

跨宿主用例（M75–M77）按[宿主兼容规则](../references/host-compatibility.md)检查资源定位与实际能力，而不是仅替换产品名称。M75 检查业务 cwd、真实 Skill 根和项目私有目录相互独立，含空格路径正确传参，已有卡片只读且不编造工具调用。M76 逐轮检查 WorkBuddy 无浏览器与原生问答时的“未实查”、文本两选项与自由输入，以及按回答续接。M77 可分别套用三个宿主名称，检查无写入/执行能力时仍给方案、风险与验收草稿，但明确源稿文件、PDF 和持久化未完成；这属于如实部分交付，不能标为完整文件交付通过。

三条是模拟能力环境的合成评测，新增案例与 JSONL 解析通过**不代表已在三个真实客户端运行通过**。执行 M75 前将占位符替换为独占临时目录和实际解释器，保留卡片哈希；M76 不访问示例域名，M77 不创建真实业务文件。记录实际可用工具与输出，不能用提示词声明“缺少工具”冒充真实客户端不支持该能力。

真实客户端手动冒烟检查按宿主分别记录，不用一个平台的结果覆盖其他平台：

| 检查项 | 验收证据 |
| --- | --- |
| 安装与发现 | 使用 README 对应安装方式，记录客户端/版本、技能版本、加载路径或导入方式；确认 `read-her-heart` 出现在技能列表或可被实际加载。 |
| 调用与引用 | 使用该宿主支持的调用入口，确认加载当前 SKILL 及需要的引用文件；从不同业务 cwd 访问模板与脚本，不能靠旧副本偶然成功。 |
| 问答与系统访问 | 有原生问答时实际选择并续接，无该能力时检查文本路径；仅对隔离测试系统做获授权只读检查，无访问工具则检查未实查说明。 |
| 文件与 Backlog | 在授权临时私有目录执行一次真实保存和新会话重新读取，核对卡片、来源及历史；无执行/写权限时只验诚实降级，不记为持久化成功。 |
| PRD 交付 | 选择类型后检查真实源稿/PDF、版本、结束标记与 FR/AC；缺导出器时记录部分交付及缺口，不把聊天链接当文件。 |

结果分开记为“结构检查”“隔离模拟行为”“真实客户端验收”，并注明通过、失败或未执行及证据。Windows 的脚本分支模拟也不代替 Windows 实机测试；客户端个人技能的结果不外推到云端或 Web 会话。

失败样本用于定位缺陷，不意味着必须把每种表面措辞写成新的硬规则。修复时优先找路由、阶段门槛或证据处理的根因，并复测相邻用例。
