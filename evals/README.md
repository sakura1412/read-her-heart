# 回归评测集

`cases.jsonl` 每行是一个独立测试：`turns` 为输入，`expected` 是应观察到的行为，`forbidden` 是不得发生的行为，`failure_example` 是**合成的典型错误输出**，不是实际运行记录。`examples/normal-end-to-end.md` 则是完整正向案例；其数字和结论只适用于该虚构输入，不是所有需求的标准答案。

使用方式：先确认待测环境已加载**本仓库当前待测版本**的 Skill；每个用例在新对话或隔离上下文运行，多轮用例按 `turns` 顺序发送。若需生成文件，使用临时可写目录并检查真实 PDF 与源稿；不要用真实账号、生产系统或私有业务数据跑这些合成用例。逐项核对所有 `expected` 与 `forbidden`，不要靠标题、固定措辞或正则命中判通过。记录 Skill 版本、是否通过、实际输出/文件证据、失败原因；改动规则前后用同一组用例比较。

最低通过要求：模式与作用范围正确；证据不足时不假装通过普通 PRD 门槛；有明确强制指令时完成方案、逐功能点 AC 与相应 PRD，保留安全和真实性边界；不编造系统实查、数据、成本或监管结论。若一个用例触发了 PRD 生成，还应检查同版本可编辑源稿、真实可下载 PDF、结束标记及 FR→AC 编号，而不只看聊天里是否宣称“已生成”。

批量需求用例还需核对：每条原始输入有稳定 ID 和处理去向；疑似重复项保留全部来源；粗筛、正式优先级与实施批准不混为一谈；硬依赖、软依赖、冲突和待确认关系不混写，依赖环不能伪装成可执行顺序。只有排期前提充分时才能承诺日期；缺研发容量、估时或发布窗口时，允许给带条件的处理波次，不得编造日历排期。强制状态仅绑定用户明确指定的需求，不传染相邻项或依赖项。

失败样本用于定位缺陷，不意味着必须把每种表面措辞写成新的硬规则。修复时优先找路由、阶段门槛或证据处理的根因，并复测相邻用例。
